# Version pinning

The Monolith's reproducibility guarantee rests on pinned build inputs. Two pins move independently: the
Gentoo tree (`TREE_COMMIT` and its companions in the `Makefile`) and the builder image (`BUILDER_DIGEST`).
The tree pin drives `configs/portage/versions.lock`; the builder pin drives `configs/portage/crossdev.lock`.
This document explains the two pins, the pin layers, how the automated tree bump works, and what to do
when a bump breaks the build.

## The two-pin model

### The builder image

The builder image holds the host build tools and the crossdev toolchain. The `Makefile` pins it by digest
(`BUILDER_DIGEST`, `BUILDER_REF`) and `make pull-image` pulls that digest. It drives:

- `configs/portage/crossdev.lock` — the `sys-libs/musl` / `sys-devel/gcc` pins passed to `crossdev --libc` /
  `--gcc`.

The builder pin moves rarely and deliberately: rebuilding the image is slow, and a new musl or gcc pin can
break the cross-toolchain build (see "When a bump breaks the build"). The rebuild and its bump flow belong
to the builder-rebuild node (M02); the tree bump described here never touches the builder pin or the
stage3 base.

### The tree pin

The tree pin is the Gentoo tree that `configs/portage/versions.lock` is generated against and that every
build resolves against. It is a commit of `github.com/gentoo-mirror/gentoo`, archived once as an OCI
artifact (`gentoo-tree:<commit40>` in the registry, `scripts/seed-tree.sh`) and restored by digest
(`make sync-portage`, `scripts/sync-portage.sh`). It is four lines of the `Makefile`:

| Line | Meaning |
| --- | --- |
| `TREE_COMMIT` | the gentoo-mirror commit |
| `TREE_DIGEST` | the manifest digest of `gentoo-tree:<TREE_COMMIT>` |
| `SOURCE_DATE_EPOCH` | the committer time of `TREE_COMMIT` (SPEC §6) |
| `TREE_FILES` | the file count of the restored tree |

`docs/tree-pin.md` is the record of rc1's tree; a bump moves the `Makefile` lines and leaves that document
alone. The cache tag of the binary packages includes `TREE_COMMIT`, so a tree move is a full rebuild.

### Which command regenerates which lock

| Lock file | Pin | Regenerated by |
| --- | --- | --- |
| `configs/portage/versions.lock` | tree pin | `make update-versions` — against the tree `make sync-portage` restores into `output/repos/gentoo` (`update-versions` depends on `sync-portage`) |
| `configs/portage/crossdev.lock` | builder pin | the toolchain flow (M02) |

## The pin layers

All three pins are checked into git and are the source of truth; this document explains them.

### 1. The `Makefile` — the tree pin and the builder pin

`TREE_COMMIT`, `TREE_DIGEST`, `SOURCE_DATE_EPOCH` and `TREE_FILES` are the tree pin; `BUILDER_DIGEST` is the
builder pin. `scripts/update-build-pins.sh` manages the tree pin and runs on the host or in the toolbox
(`git`, `curl`, `oras`, `zstd`, `jq`); it needs no Docker and makes no request to `distfiles.gentoo.org` or
Docker Hub.

```sh
scripts/update-build-pins.sh check                # newest gentoo-mirror/gentoo commit; NO-OP when it is TREE_COMMIT
TARGET_COMMIT=<c40> scripts/update-build-pins.sh check   # the same, for a given commit
scripts/update-build-pins.sh update <commit40>    # write the four pin lines for an archived commit
```

`check` asks `git ls-remote` for the mirror's `HEAD`. `update` reads the digest of `gentoo-tree:<commit>`
with a read-only `oras manifest fetch`, takes the committer time from the manifest's
`org.opencontainers.image.created` annotation (the GitHub commits API is the fallback), counts the files of
the archive `oras pull` returns, and rewrites the four lines. It never writes to the registry: archiving is
`make seed-tree` (`scripts/seed-tree.sh`), which the workflow's `archive` job runs.

`BUILD_EPOCH` is not part of a tree bump; the build version label keeps its own rules.

### 2. `configs/portage/versions.lock` — world package versions

The world packages (`configs/portage/world`) are pinned as `category/package:version:slot`. Regenerated by
`scripts/update-versions.sh update`, which runs inside the builder container and asks portage itself
(`portageq best_visible`) what the best visible version of each world package is in the pinned tree.

```sh
make update-versions     # sync-portage (restore the pinned tree), then regenerate inside the builder
```

### 3. `configs/portage/crossdev.lock` — musl + gcc cross-toolchain pins

Two lines: `sys-libs/musl` and `sys-devel/gcc`, in the same `category/package:version:slot` format. They are
cross-toolchain-specific (passed to `crossdev --libc` / `--gcc`) and are not world packages, so they are
pinned separately. `binutils` is a world package and lives in `versions.lock`; `linux-headers` is derived at
build time from the kernel version's major.minor (see `Makefile`). A tree bump does not regenerate this
lock; the toolchain flow (M02) does.

## How the automation works

`.github/workflows/pin-bump.yml` runs weekly (Mondays 06:00 UTC, three hours after `build.yml`'s own weekly
build at 03:00 UTC, so that run's cache is warm) and on manual `workflow_dispatch`, with an optional
`target_commit` input to force a gentoo-mirror commit instead of the newest one.

```
archive (contents: read, packages: write; no App token)
  │  make pin-check        scripts/update-build-pins.sh check
  │       newest commit == TREE_COMMIT: NO-OP in the job summary, the bump job does not run
  │  make pin-tree-exists  is gentoo-tree:<commit> in the registry?
  │  make pin-seed         if not: scripts/seed-tree.sh <commit> (the only registry push)
  ▼
bump (contents: write, pull-requests: write, packages: read; App token)
  │  1. mint an App installation token (actions/create-github-app-token)
  │  2. check out with that token; create the labels; create pins/bump-<old12>-<new12>
  │  3. make update-build-pins   write TREE_COMMIT, TREE_DIGEST, SOURCE_DATE_EPOCH, TREE_FILES
  │  4. make sync-portage        restore the new tree
  │  5. make update-versions     regenerate versions.lock against it
  │  6. make pin-commit          commit the Makefile and versions.lock, push the branch
  │  7. make pin-pr              open a PR against main, labeled pin-bump and full-ci
  ▼
the PR's own run of build.yml (pull_request, full-ci) validates it:
  build, attestation (SBOM, licence and CVE gates), boot tests
  a human reviews and merges; nothing in this pipeline merges
```

The bump pushes with a GitHub App token, not `GITHUB_TOKEN`: a push or PR made with `GITHUB_TOKEN` starts
no workflows, so the PR's Build run would never start. The App token cannot push to the container registry,
which is why the registry push is a separate job with `GITHUB_TOKEN` and `packages: write` and nothing else
that is privileged. The App's id is the repository variable `PIN_BUMP_APP_ID` and its private key the
secret `PIN_BUMP_APP_PRIVATE_KEY`; the owner creates and installs the App.

`update-versions` regenerates `versions.lock` inside the builder container, so on the runner it is owned by
root and `git add` fails to index it. `make pin-commit` reclaims `configs/portage` with `sudo chown -R`
before staging.

`build.yml` stays the one definition of how The Monolith is built and validated. The PR opened with the
`full-ci` label gets its Build run through the existing pull-request gate; `pin-bump.yml` neither dispatches
it nor waits for it, so any job `build.yml` gains later is part of the validation without a change here.
(`build.yml` is not a `workflow_call` target: GitHub binds a Sigstore signing certificate to the entry
workflow, and a called `build.yml` would fail to attest.)

A bump changes only the tree pin lines of the `Makefile` and `configs/portage/versions.lock`. The tree move
is a full rebuild: the PR's run is cold, and `main` pays another after the merge.

## Cadence and manual overrides

- **Automatic:** every Monday 06:00 UTC.
- **Manual, newest commit:** Actions → "Pin Bump" → *Run workflow*, leave `target_commit` empty.
- **Manual, forced commit:** the same, with `target_commit` set to 40 hex digits of a gentoo-mirror commit.
- **Fully manual / local, no CI:**
  ```sh
  make seed-tree TREE_COMMIT=<c40>     # archive the commit (registry login first); skip if the tag exists
  make update-build-pins NEW_COMMIT=<c40>   # write the four pin lines
  make update-versions                 # sync-portage (restore the new tree) + regenerate versions.lock
  ```
  `make update-all NEW_COMMIT=<c40>` runs the last two. `make check-updates` shows the package versions
  available now against the `versions.lock` pins.

## When a bump breaks the build (the fixup loop)

A new tree can shift package versions in ways that break the build: a portage mask change, a new musl or
gcc that fails against the kernel headers pin, an ebuild that no longer applies. The policy:

1. The bump PR is opened with its failing Build run visible on it. When `make update-versions` fails
   against the new tree, the bump job still pushes the branch and opens the PR, labelled `needs-fixup`, with a
   BLOCKED note in its body (`versions.lock` is then unchanged).
2. A human (or an agent) fixes forward on the **same branch** (`pins/bump-<old12>-<new12>`): adjust
   `package.mask`/`package.unmask` entries, tweak `configs/overlay/**` ebuilds, or hand-edit a lock entry,
   then commit directly to that branch. The `needs-fixup` label marks it.
3. A push to the branch re-runs the Build run, since the PR carries `full-ci` (`synchronize` re-runs it).
4. Repeat until green, then merge the PR normally. Nothing in this pipeline merges on your behalf.

## The toolchain bump

The builder image is rebuilt by `.github/workflows/toolchain-bump.yml`, run by hand (`workflow_dispatch`).

- **Pins.** `TREE_COMMIT_TOOLCHAIN` and `TREE_DIGEST_TOOLCHAIN` in the `Makefile` name the tree the image bakes in.
  They are empty until the PR of the first dispatch writes them. While either is empty, `make build-image` fails.
- **Inputs.** `tree_commit` is the 40-digit commit of the tree. `first_rebuild` rebuilds at the current
  `TOOLCHAIN_EPOCH`. Without it, the run stops when the epoch is unchanged.
- **Archive.** The `archive` job stores the tree as `gentoo-tree:<commit40>` when the registry lacks it.
- **Tags.** The image tag is the epoch, a hash of the `Dockerfile` and the first 12 digits of the tree commit.
- **No merge.** The workflow opens a PR and never merges it. A human reads it first.
- **New epoch.** The `FROM` line of the `Dockerfile` names the stage3 image by digest. A new epoch needs a new stage3
  digest in that `FROM` line and a mirror of the image first. Until then, the pin script refuses a changed epoch.

## Caveat: `savedconfig` changes require a binpkg purge

`build.yml` restores the per-package binary packages (`.gpkg.tar`) from the registry store
(`scripts/binpkg-store.sh`, `${REGISTRY}/binpkgs:<cache tag>`) and builds with `--usepkg`
(`scripts/build-packages.sh`). Portage's binpkg reuse keys on **version + USE flags + CHOST**; it does
**not** hash `savedconfig` contents. So editing a `savedconfig`-governed package's config **without bumping
its version** yields a binpkg Portage treats as identical to the cached one, and the **stale binary (built
with the old config) is silently reused**; the config change never takes effect in the built image.

Packages this affects in this repo:

| Package | Config file |
| --- | --- |
| `sys-apps/busybox` | `configs/portage/savedconfig/sys-apps/busybox` (applet set, e.g. `CONFIG_FINDFS`) |
| `sys-kernel/monolith-kernel` | `configs/kernel.config` |

**When you change one of these configs, purge its cached binpkg for the current cache tag before the next
build** (or the change is a no-op): remove the package's gpkgs from the store artifact, or bump the
package's revision. A tree move changes the cache tag (it includes `TREE_COMMIT`), so it invalidates every
cached binpkg naturally. A durable fix would be to opt `savedconfig` packages out of binpkg reuse
(`emerge --usepkg-exclude`) or to key the cache on a config hash. (`busybox` is cheap to rebuild every
time; the kernel is not, which is why this is a purge-on-change rule rather than an unconditional rebuild.)

## Files

| File | Purpose |
| --- | --- |
| `Makefile` | the tree pin (`TREE_COMMIT`, `TREE_DIGEST`, `SOURCE_DATE_EPOCH`, `TREE_FILES`) and the builder pin (`BUILDER_DIGEST`) |
| `configs/portage/versions.lock` | the world package version pins, resolved against the pinned tree |
| `configs/portage/crossdev.lock` | musl + gcc cross-toolchain pins, tied to the builder pin |
| `docs/tree-pin.md` | the record of rc1's tree |
| `scripts/seed-tree.sh` | archives a gentoo-mirror commit as `gentoo-tree:<commit40>` |
| `scripts/sync-portage.sh` | restores the pinned tree by digest; run via `make sync-portage` |
| `scripts/update-build-pins.sh` | resolves the newest commit (`check`) and writes the tree pin lines (`update <commit>`) |
| `scripts/pin-bump-pr.sh` | the bump job's labels, branch, commit and PR steps (`make pin-*`) |
| `scripts/update-versions.sh` | container-side: regenerate `versions.lock` against the restored tree |
| `.github/workflows/pin-bump.yml` | the weekly/manual automation described above |
| `.github/workflows/build.yml` | the build + attestation pipeline that validates the PR |
