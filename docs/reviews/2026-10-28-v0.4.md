# Revision v0.4 — 2026-10-28

## Why

The owner asked for one guiding principle: **we are building a small, specialized Gentoo-derived
distribution, not a new distribution-building framework.** That principle came with six priorities:
1. Port first, simplify second.
2. Let Portage do its job.
3. Treat the custom ebuilds as a conventional overlay.
4. Prefer standard tools.
5. Keep the scope to the distro and its factory.
6. Keep the real constraints.

v0.3 failed that test. It had 52 nodes and 763 acceptance criteria, and it specified a large amount of
new machinery around a factory that already works:
- a storage abstraction with a contract suite;
- a content-addressed build cache with per-package fingerprints, consistent sets, a whole-build memo and
  rc1 seeding (I06 alone had 17 ACs);
- a system inventory, a graph validator, an agent loop and commit-identity CI;
- a kernel-fragment toolchain and a pin ledger.

Most of that machinery reimplemented something Portage, GitHub or an OCI registry already provides.

v0.4 has 20 nodes and 127 acceptance criteria. Thirteen nodes are on the path to the first reproducible
release, and the longest chain is seven nodes. The node specs total about 850 lines, against about 8,200 in
v0.3. Each custom subsystem that remains is justified in SPEC §5: the standard mechanism
considered, the gap, and the smallest fix.

## What stayed from v0.3

- **The predecessor inventory and study.** `docs/study/` is unchanged.
- **The release oracle:**
  - the 17 boot modes, ported unchanged;
  - artifact doctrine checks;
  - the SBOM and the licence, CVE and unowned gates;
  - the rc1 lane;
  - the SBOM diff against rc1, now a release report.
- **Artifact preservation:**
  - rc1's builder and binpkg cache are copied by digest;
  - the tree is archived;
  - each release archives its distfiles and publishes `release-inputs.json`.
- **Provenance:** Sigstore SLSA attestation of the ISO digest and a mechanically checked digest chain,
  now generated by the platform (`actions/attest-build-provenance`).
- **The verified predecessor bugs:** each is fixed in a named node (table below).
- **The constraints:** i486, static musl, 64 MB, the hardware matrix, reproducibility and the CD budget.
  SPEC §1 gives each one a check.

## What changed in SPEC.md

- §0: "a distribution, not a framework"; the knowledge-content projects are explicitly out of scope; so
  are the dashboard and boot demo.
- §1 adds a constraints table with checks:
  - the CD budget is new, at 681,984,000 bytes for now (OD-16);
  - the static-musl violation list may only shrink.
- §2: nine principles. These are gone:
  - the storage interface;
  - the system inventory;
  - executable-doctrine bookkeeping;
  - the two-tier TDD rule;
  - one identity per actor.

  These are new: "a Gentoo derivative, not a framework" and "no storage vendor in the build path"
  (without an abstraction layer).
- §4: the predecessor's layout is kept (`configs/overlay`, `configs/portage`, `scripts/`) instead of a
  new tree. §4.3 adds the overlay boundary rules.
- §5 is new: the standard-mechanism table, which replaces the store contract and the build-cache design.
- §6: pins stay where the predecessor kept them. Three pins change: tree commit, builder digest,
  registry. Registry objects are listed, with nothing deleted automatically.
- §7: the oracle is unchanged in substance; the release reports and the reproducibility check are added.
- §8: CODEOWNERS and branch protection replace the trusted-base checker and the identity allowlist.
- §9: a shorter template. "Standard mechanism" and "Changes from the port" replace "Design" and
  "Traps", and there is no RED plan or cost section.
- §10: OD-3, 4, 5, 7, 10 and 14 are withdrawn. OD-1 is now only the URL. OD-2 is now about prereleases.
  OD-16 is added.

## Decisions taken in this revision

- **No custom build cache.**
  - Portage's own binary packages, with `--binpkg-respect-use`, `--binpkg-changed-deps` and
    `--rebuild-if-unbuilt`, do the work.
  - The predecessor's one-artifact-per-PKGDIR transport and savedconfig marker are ported.
  - The cache tag adds a hash of the global config files Portage cannot see.
  - Overlay edits need a revbump, as in Gentoo.
- **No rc1 seed.** rc1's cache was built across many commits under one epoch, so its entries need not
  match `b9f533b`'s config. One cold build (~78 min, measured) costs less than proving the seed sound.
  The cache is preserved for comparison.
- **No storage abstraction.** OCI is already a standard, portable protocol. The registry location is one
  variable.
- **Kernel config through `savedconfig.eclass`.** This replaces the predecessor's bind-mounted file:
  that file silently fell back to `allnoconfig` and was written back into the repo. It also replaces
  v0.3's fragment split.
- **Platform-generated provenance.** `actions/attest-build-provenance` replaces the predecessor's own
  `generate-provenance.py`. This is a replacement with a demonstrated benefit: the provenance is no
  longer written by the build it describes.
- **Distfiles:** one archive per release, not a mirror service. The two Rust packages move to
  `cargo.eclass` `CRATES` (R02), so their crates are archived too.
- **`SOURCE_DATE_EPOCH`** is the committer time of the tree commit (SPEC §6).
- **The advisory feed is hosted on GitHub Pages** under the OD-1 name (new OD-1 default). A custom domain
  there needs no stored cloud key, which keeps SPEC §8's rule.
- **No automatic registry deletion** until storage costs money. The predecessor's GC deleted epochs.

## Corrective pass (2026-10-28, before merge)

The owner kept the architecture and asked for six corrections:
1. **Bit-for-bit reproducibility is a hard release gate.** Two clean, separate, offline builds from the
   same pinned and archived inputs must produce the same ISO SHA-256. Any mismatch fails the release.
   diffoscope is a diagnostic only. The known-differences list is gone (SPEC §1, §5, §7; P02).
2. **The gate comes before publication.** The order is now fetch → two builds → compare and oracle →
   attest → publish. P02 is the gate and P01 depends on it. MS2 is after P01, and nothing is pushed or
   published before the gate passes (P02-AC-3).
3. **No network for sources in release builds.** R05 is new and critical: `rl144` and `stele` move to
   `cargo.eclass` `CRATES`, including the standard library's crates for `-Z build-std`. Release builds run
   with `--network none` and Portage fetching disabled.
4. **"From source" is proven.** Release mode runs `--emptytree`, skips `quickpkg`, and audits every
   shipped file against packages merged from source in that run. The only exception is a declared list
   of crossdev toolchain files, provenance `BUILDER_DIGEST` (B01 changes 8–10).
5. **Revision discipline before the cache.** R04 is new and critical: a minimal git-diff check that runs
   before B01. `pkgcheck` stays in R02, later.
6. **Spec errors.** B03-AC-7 and M01 said `master` instead of `main`. F01-AC-3 and AC-6 assumed the
   predecessor's commit exists in this repository; the slow half now fetches it by full SHA from the
   predecessor and checks the tree id.

Graph after the pass: 22 nodes, 15 critical, longest chain still seven
(`F01 → I01 → I02 → B01 → B03 → P02 → P01`).

**Genuine obstacles, reported rather than weakened:**
- **The amount of nondeterminism is unknown** until the first double build. The predecessor never built
  twice. The MS2 calendar therefore has an open row.
- **Offline `-Z build-std`** for a custom target with vendored std crates is unverified for the pinned
  nightly. R05 lists the owner's options if it cannot work; none relaxes the offline rule.
- **Portage VDB metadata on the disc** (`BUILD_TIME`, `COUNTER`, saved environments) may vary between
  builds. If Portage does not honour `SOURCE_DATE_EPOCH` there, `build-rootfs.sh` normalises the shipped
  copy (P02 change 6).
- **`--emptytree` inside a crossdev sysroot** may try to re-merge crossdev-placed packages. Each such
  case is fixed or declared with its host owner, never silently reused.
- **The toolchain is trusted by digest, not rebuilt per release.** musl `libc.a`, `libgcc.a` and
  `libatomic.a` are linked into every binary from the pinned builder image. This does not affect ISO
  reproducibility, because both builds use the same digest. M02 later makes the image itself rebuildable.

## Second corrective pass (2026-10-28, before merge)

The owner set three scope changes:
1. **Strict determinism waits until the system is constituted.** P02 moves to the `later` track, after
   P01 and before cutover (X01 depends on it). The first release is one offline from-source build. The
   fetch job, the distfiles archive, `release-inputs.json`, the offline release mode and the rule that
   nothing is attested or published before the gates pass move from P02 into P01 (P01 changes 1, 2, 6;
   AC-4, AC-11, AC-12). P02 keeps the second build, the comparison and every nondeterminism fix, unchanged
   in substance. MS2 is renamed `first-release`.
2. **`rl144` and `stele` become their own node after the fundamentals.** R05 moves to the `later` track,
   after P01. Until then B01 takes the two packages out of `world` (B01 change 11, AC-13), B03 runs every
   boot mode except `stele-acid2`, and P01's rc1 diff carries two reason lines naming R05. R05 restores the
   packages and the mode (R05 change 4, AC-5). X01 depends on R05, because cutover replaces a predecessor
   that shipped both. Offline `-Z build-std` is no longer on the path to the first release.
3. **`--emptytree` is replaced.** A release build runs in a fresh container from the builder image with an
   empty `PKGDIR`, so the only packages it could reuse are the ones the image preinstalled in the target
   root. B01 now names exactly those on the emerge command line with `--oneshot`, which Portage always
   re-merges. `--emptytree` would re-merge the same set plus anything crossdev placed in the target root,
   and in a cross build it may also pull build-host dependencies into the graph. The source audit, which is
   the actual proof, is unchanged (B01 change 8, AC-10).

Also fixed: the tag pipeline is now `build.yml`'s tag path, not a separate `release-gate.yml`. Signing
binds to the entry workflow (`build.yml:1-17`), and X01's README command names `build.yml` as the signer
workflow, so a separate entry workflow would have broken verification.

Graph after this pass: 22 nodes, 13 critical, 144 acceptance criteria, longest chain six
(`F01 → I01 → I02 → B01 → B03 → P01`).

## Milestone order (2026-10-28, before merge)

The owner set the order without changing the design:
- **MS1 is the first goal:** a working, repeatable, testable ISO for iteration, as early as possible
  (`iteration-iso`, after B03). It may leave out `rl144` and `stele` (B01 change 11), runs 16 of the 17
  boot modes, and is never published or called a release.
- **Nothing is a release before MS2,** which needs bit-for-bit reproducibility and all 99 world packages.
  P02 and R05 are back on the critical path, side by side after B03, and P01 depends on both. P02 owns the
  fetch job, the archive, `release-inputs.json` and the offline mode again; P01 attests and publishes
  after the gate. P01 gains a package-set check against the predecessor's 99 world atoms (change 6,
  AC-11). R05's third fallback, leaving the two packages off the disc, is removed.
- **Kept from the second pass:** the tag pipeline lives in `build.yml`; B01 re-merges the builder image's
  preinstalled packages with `--oneshot` instead of `--emptytree`.
- **Step 0 no longer blocks porting.** F01 needs only the schedule stop; the GHCR copy is needed before
  I03 and branch protection before the first merge.

Graph: 22 nodes, 15 critical (12 of them lead to MS1), 143 acceptance criteria. Longest chain to MS1 is
five (`F01 → I01 → I02 → B01 → B03`), to MS2 seven (`… → B03 → P02 → P01`).
