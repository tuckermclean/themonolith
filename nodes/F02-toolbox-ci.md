## Purpose
Every CI job runs its commands through `toolbox/run`, which pulls `${REGISTRY}/toolbox:<inputs>` and builds the image from `snapshot.debian.org` only when that pull fails. From 2026-11-06 to 2026-11-09 main's `toolbox-image.yml` never published the tag (an apt build killed with exit 137 in run 42142989491, then `denied: permission_denied: write_package` in run 42691476669, because the package was linked to no repository), so every job of every pull request rebuilt the toolbox, until `snapshot.debian.org` answered `TooManyRequests 503 No healthy backends`. Node sessions lost CI runs to it and reported a snapshot outage; the one trace was a stderr line. The owner fixed the package by hand (run 42719616205). After this node a fallback build in Actions is a visible warning that says whether it was expected, a pull request whose toolbox inputs are main's fails `pr-validate.yml` while main's tag is missing, a workflow run builds the toolbox at most once and hands it to its other jobs, and apt retries a failed download with a bounded wait.

## Standard mechanism
GitHub Actions workflow commands (`::warning::`) and the `GITHUB_STEP_SUMMARY` file report the fallback. The OCI distribution API answers whether a tag exists: GHCR's anonymous token endpoint (`https://ghcr.io/token?scope=repository:<owner>/<repo>/toolbox:pull`) and a `HEAD` or `GET` of `/v2/<owner>/<repo>/toolbox/manifests/<inputs>`, with `curl` (or `oras manifest fetch`, already in the toolbox); no token is needed, as I01-AC-4 requires of every package. `podman save` / `docker save`, `actions/upload-artifact` and `actions/download-artifact` move the image between the jobs of one run, as B03 moves its ISO. APT's own `Acquire::Retries` (and its delay settings) retry a failed download. Custom code: one short check script (change 2), a few lines of notice in `toolbox/run` (change 1) and two Make targets (change 3). The gap: nothing standard says whether a missing image was expected.

## Changes from the port
Nothing is ported. These are the changes to this repository's files.

1. **A fallback build is loud in Actions.** When `toolbox/run` finds no local image, cannot pull `${REGISTRY}/toolbox:<inputs>` and `GITHUB_ACTIONS` is `true`, it prints a `::warning::` annotation and appends a line to `GITHUB_STEP_SUMMARY` (when set), each naming the tag it tried and saying one of: the branch changes `toolbox/Containerfile` or `toolbox/selfcheck` against its base, so the build is expected; the inputs are the base's, so main's image is missing and `toolbox-image.yml` (Toolbox Image) has not published it; or the base could not be read. The base is the pull request's base commit (`BASE` where the job sets it, else the base branch, fetched if the checkout lacks it), and `origin/main` outside a pull request. Outside Actions it prints the current stderr line and nothing more. *AC-1, AC-6.*
2. **A missing main image fails `pr-validate.yml`.** `make toolbox-check` runs `scripts/toolbox-check.sh` with `BASE`. When `toolbox/Containerfile` and `toolbox/selfcheck` at `HEAD` equal those at `BASE`, it asks the registry anonymously for `toolbox:<inputs>`: present passes; absent fails with a message naming the tag and the Toolbox Image workflow; an answer that is neither (a network error, a 5xx) fails with that answer, never as present. When the inputs differ, it passes without asking and says the build is expected. `pr-validate.yml`'s `validate` job runs it with `BASE` set to the pull request's base. The canary is not used: its `paths:` filter skips most pull requests. *AC-2, AC-6.*
3. **One job per workflow run builds or pulls the toolbox.** Every workflow that runs the toolbox in more than one job of a run (today `build.yml` with the `boot-test.yml` it calls, `boot-test-rc1.yml` with `boot-test.yml`, `artifact-checks-rc1.yml`, `sbom-gates-rc1.yml` and `boot-test-repeat.yml`) gets one `toolbox` job that pulls or builds the image and saves it (`make toolbox-save`) as an artifact of the run, with a short retention. Every other job of the run that runs `toolbox/run` (directly or through a Make target) needs that job, directly or through its caller, and loads the image (`make toolbox-load`) before its first other `run:` step, so `toolbox/run` finds the local image and neither pulls nor builds. A reusable workflow's jobs load the caller's artifact. Workflows with one job keep pulling or building as they do now. Nothing is shared by pushing: `toolbox-image.yml` stays the only workflow that publishes, from `main` and `workflow_dispatch` only, and no pull request workflow gets `packages: write` for the toolbox. *AC-3, AC-4, AC-6.*
4. **apt retries with a bounded backoff.** `toolbox/Containerfile` writes its retry settings (a retry count and a bounded wait between attempts) where both its `apt-get update` and `apt-get install` use them, and where the image keeps them for AC-5's test: a file under `/etc/apt/apt.conf.d/`, or, if APT's own retries do not cover an HTTP 503, a small wrapper that the Containerfile writes into the image (`/usr/local/bin/apt-retry`, which re-runs a failed apt command with a bounded wait between attempts), runs apt through and the image keeps. The Containerfile writes it itself rather than copying a file from `toolbox/`, because `<inputs>` hashes only `toolbox/Containerfile` and `toolbox/selfcheck`: a copied file could change without changing the tag. APT 3.0.4 in the toolbox does not retry a 503 (`Acquire::Retries=3` still asks each path once and fails), so the wrapper is the one used. This changes the toolbox inputs, so this node's own pull request exercises the expected-build path of changes 1 to 3. *AC-5, AC-6.*

## Risks
- After a pull request that changes the toolbox inputs merges, main's publish takes some minutes. A pull request whose base is that new `main` fails `toolbox-check` until the publish finishes; the message names the workflow, and a re-run passes once it has. This is AC-2 working as intended, not a flake.
- `toolbox-check` makes `pr-validate.yml`, a required check (SPEC §8), depend on GHCR answering. It already does: the `validate` job pulls the toolbox from GHCR.
- APT 3.0 (trixie) retries transient errors with a growing delay (`Acquire::Retries::Delay`), but APT 3.0.4 does not count an HTTP 503 as transient: with `Acquire::Retries=3` it asks each path once, then moves to the next candidate file, then fails. Change 4 therefore uses its wrapper; AC-5 holds either way. The wrapper's waits are short because `make test-unit` runs AC-5's test in every commit-less copy of `scripts/tests/make-test.test.sh`.
- The toolbox image is large (QEMU, OVMF, diffoscope-minimal, pkgcheck). An artifact of it per run costs upload and download time in every job and counts against the repository's artifact storage; a retention of one day bounds the storage. If loading the artifact proves slower than pulling from GHCR, change 3 may let the `toolbox` job hand over only when its pull failed, with the other jobs pulling as now; AC-3 and AC-6 then say "loads it or pulls it", which is a spec change.
- `toolbox/ci run` shares one checkout between jobs, so it shows the save and load steps run but not the artifact transfer; AC-6 is the proof (SPEC §7).
- `.github/workflows/*` changes need a push with the `workflow` scope (AGENTS.md Traps).
- Workflows that later nodes add (P01's `release.yml` and attestation job, M01's `pin-bump.yml`, P03's `advisory-feed.yml`) fall under AC-3's test as soon as they run the toolbox in more than one job.
