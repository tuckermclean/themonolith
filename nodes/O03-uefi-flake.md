## Purpose
In CI, the `uefi` boot of B03's built ISO failed in 2 of 7 boots, and both failures were identical: `perl /usr/lib/cgi-bin/guestbook.cgi` exits 255 compiling `/usr/lib/perl5/5.42.0/i486-linux/Config.pm` ("character \x80; marked by <-- HERE … line 1", through `CGI.pm`, `if.pm` and `deprecate.pm`), while the `CGI.pm param()` check just before it, which loads the same chain, passes. The two failures are run 42428425660 attempts 1 and 5. The passes are run 42416838904, run 42428425660 attempts 2 and 6, run 42448686665 and run 42502182433. Attempts 2 and 6 re-ran only the failed jobs, which download the run's existing ISO artifact (B03 change 1), so the same ISO bytes failed in one attempt and passed in the next. Every local boot passed (26 `uefi` boots of two CI ISOs, and 120 perl runs in two stress boots), as did all 9 `uefi` attempts of `boot-test-rc1.yml`. After this node a failing check leaves the evidence to tell a disc fault from a fault in the guest or emulator, the cause is found from a recorded failing run and fixed where it lies (or the failure is recorded as not reproduced), and the `uefi` mode is green 20 times in a row in CI. P01 depends on it: the first release gates on all 17 modes.

## Standard mechanism
The ported harness (`boot-test.py`, O01) and GitHub Actions, as O01 and B03 use them: `actions/download-artifact` with `run-id` and `github-token` to fetch a finished `build.yml` run's ISO, a job matrix for repeated boots, `sha256sum` and `dmesg` in the guest's busybox, and `unsquashfs` in the toolbox for the comparison with the disc. No gap is recorded. The only new code is the evidence of change 1, a few lines in `run_check`'s callers.

## Changes from the port
`boot-test.py`, `boot-test.yml` and the `test-boot` target stay as O01 and B03 left them except for these changes.

1. **A failing check leaves evidence.** A check may name the files its command reads. When such a check fails after `/init`, the harness runs, in the same boot and before the next check, `sha256sum` on those files, the last 50 lines of `dmesg`, and the check's command once more, and prints all of it with the failure. The second run is evidence only: the check stays `FAIL` whatever it gives. The `CGI.pm param()` and `guestbook.cgi` checks name `/usr/bin/perl`, `/usr/lib/cgi-bin/guestbook.cgi`, `/usr/lib/perl5/5.42.0/CGI.pm`, `/usr/lib/perl5/5.42.0/if.pm`, `/usr/lib/perl5/5.42.0/deprecate.pm` and `/usr/lib/perl5/5.42.0/i486-linux/Config.pm`. The hashes, compared with the same files in the run's squashfs, say whether the guest read the bytes on the disc; the second run says whether the fault persists in that boot. Reason: no failed boot has been available to compare, and #46's open question is which side of that boundary the fault is on (D-state-and-no-hidden-stderr). *AC-1.*
2. **The runner's CPU is recorded.** `make test-boot` appends the host's `/proc/cpuinfo` `model name` and `flags` lines (the first CPU's) to `output/tool-versions.txt`, which every mode job already uploads. Reason: under TCG the host CPU is the one input that differs between CI runners and was never recorded (#46). *AC-2.*
3. **Repeated `uefi` boots without a rebuild.** `boot-test-repeat.yml` is a `workflow_dispatch` workflow with inputs `build-run-id` (a finished `build.yml` run) and `count`. Its matrix of `count` jobs each downloads that run's ISO artifact, runs `make test-boot MODE=uefi` on it and uploads its serial log and `tool-versions.txt` under a name that carries its matrix index. It passes `toolbox/ci lint`. Reason: AC-5 needs many `uefi` boots, and a full build per boot costs a build each time. *AC-5.*
4. **The fix lies where the cause is.** When AC-4's record names a cause in this repository, the fix is made in the file that holds it: B01's perl recipe, B02's kernel config, or O01's `boot-test.py`. The record names the file and the line. A cause outside these (QEMU, OVMF or the toolbox pins, the runner image) goes to the owner as a spec change before anything is changed. *AC-4, AC-5.*

## Gate
- **O03-AC-1** — When a check that names files fails, its reported detail contains a `sha256sum` line for each named file, the `dmesg` tail, and the exit code and output of a second run of its command, and the check's result is still `FAIL` when the second run passes. A check that passes runs nothing extra. The `CGI.pm param()` and `guestbook.cgi` checks name the six files of change 1. *Verify:* `scripts/tests/boot-test-evidence.test.sh` (fake child whose first run of the guestbook command fails and second passes).
- **O03-AC-2** — `make test-boot` writes `output/tool-versions.txt` with one `model name` line and one `flags` line from the host's `/proc/cpuinfo`, after the QEMU and OVMF lines O01 records (O01-AC-5). *Verify:* `scripts/tests/boot-test-evidence.test.sh` (`make -n test-boot`); `grep -c '^model name' tool-versions.txt` on a `uefi` artifact of an AC-5 run.
- **O03-AC-3** — Nothing hides the failure. `should_retry_launch` still never relaunches after a failure that came once `/init` was reached (O01-AC-1); the `uefi` mode still runs the `CGI.pm param()` and `guestbook.cgi` checks with their `contains` validators and commands unchanged; and `build_uefi_cmd` still runs `qemu-system-x86_64` with no `-cpu` argument and `-m 512` by default. A change to any of these needs a spec change first. *Verify:* `scripts/tests/boot-test-retry.test.sh` (unchanged); `scripts/tests/boot-test-evidence.test.sh`.
- **O03-AC-4** — `docs/evidence/uefi-flake.md` lists every CI `uefi` boot of a built ISO from #46's seven to the end of AC-5, each with its job URL, ISO sha256, runner CPU model and result, and states one of two outcomes. (a) A failing boot with change 1's evidence: what the hashes (compared with `unsquashfs` of that run's squashfs), the second run, the `dmesg` tail and the runner CPU show; the cause; and the fix with its file (change 4). (b) If no `uefi` boot fails once change 1 is in place, up to the end of AC-5's 20 consecutive passes, that record is the outcome, and #46 is closed as not reproduced. *Verify:* the file, linked in the PR table, with every run URL it cites.
- **O03-AC-5** — With changes 1 and 2 in place, and the fix of AC-4 (a) if there is one, 20 consecutive CI `uefi` boots pass on GitHub-hosted runners. They boot ISOs built by `build.yml`, at least two different ISOs among them, through `boot-test.yml` or `boot-test-repeat.yml`. A failing boot restarts the count and goes into AC-4's record, and no failed job is re-run to turn it into a pass. *Verify:* the run URLs in `docs/evidence/uefi-flake.md`, recorded in the PR table.

## Risks
- At the observed rate (2 in 7) the chance of 20 passes in a row with the fault still there is about 0.1%. At a much lower true rate, AC-5 can pass on a fault that is still present; AC-4 (b) records it as not reproduced, and #46 can be reopened from a later failure's evidence.
- A fault that recurs with evidence that does not show its cause keeps AC-5 from passing and so blocks P01. The owner chose that #46 gates the first release; such a record comes back to the owner.
- Leads from #46, not tested: a guest memory fault seen only with `qemu64` and 512 MB (the `bios` modes run the same perl checks with `-cpu 486` and 64 or 256 MB and never failed), and the CI host's CPU under TCG. A `uefi` boot with `-cpu 486`, or a `bios` boot with `-m 512`, would separate the two once a failure can be caught; they are diagnosis runs and are not counted in AC-5.
- `download-artifact` across runs needs `actions: read` and the ISO artifact's retention (B03 Risks); `toolbox/ci lint` acceptance of `run-id` and `github-token` inputs is unverified.
