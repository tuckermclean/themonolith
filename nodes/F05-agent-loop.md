## Purpose
After F05, one command, `/node <ID>`, drives a node from its spec to a reviewed PR: a fresh tester writes RED, a fresh implementer makes it GREEN, a fresh reviewer judges, and the orchestrator records evidence in the PR body. The roles are fenced by a hook that makes the cheap mistakes (editing frozen tests, touching protected paths, merging, rewriting history, changing identity) fail before they reach CI. Milestone MS1 is reached: later nodes can be built test-first with F04 enforcing the result.

## Scope
In:
- The `/node` skill (orchestrator procedure) and the three role agents.
- The guard hook for roles and for the whole session.
- `PROVENANCE.md` stating exactly what was copied from strange-company and what changed.
- Three small host-side tools: a brief generator, an attempt counter, a status validator.
- `docs/status.yaml`, the record of which nodes are done.

AGENTS.md (F01) keeps the one-line lesson ("a git error is not a missing checkout; capture it before concluding"). F04's `agent-env.sh` carries the identity half.

### The `/node <ID> [AC ids]` procedure
0. Preconditions (stop and say what is missing):
   - Working tree clean; default branch current (`git symbolic-ref refs/remotes/origin/HEAD` gives the name; nothing is hard-coded).
   - `make check` passes on the default branch (otherwise the next RED is judged against a broken base).
   - `graph-check.py --ready docs/status.yaml` lists the node (all deps `done`, any `decision:` settled by a `docs/decisions/` record `Resolves: OD-n`). A node with an unsettled OD does not start; ask the owner.
   - Create branch `node/<ID>-<name>` (SPEC §11). Source `tools/ci/agent-env.sh` so commits carry the bot identity.
1. Brief: `python3 -I tools/agent/brief.py <ID> [ACs]`. Split a node into slices of 3 to 8 related ACs; each slice runs steps 2 to 5.
2. RED: dispatch a fresh `node-tester` with the brief path and the slice's AC ids. Before accepting, the orchestrator checks: `git show --stat <red>` touches only test paths; subject `test(<ID>): ...` with exactly one `TDD-Red-Target:` trailer; running the target at that commit with the trusted runner exits 1 with only new or changed tests failing (`tools/ci/tdd-check.py` on the one commit). An AC that already passes is reported `already_satisfied` and dropped. A slow-tier-only AC gets a `TDD-Slow-Only` commit instead. `blocked` goes to step 7.
3. GREEN: `attempts.py check` chooses the model; dispatch a fresh `node-implementer` with the brief, the RED SHA, the target and the failing test ids (on retry: every earlier review finding and failed diff SHA, so attempt 4 is not a replay). Orchestrator checks: target passes; `make check` passes; `git diff <red>..HEAD` shows no change to frozen tests. Push (the orchestrator pushes, never a role). Wait for CI; for every AC with tier slow, wait for the named CI job and record its run URL. A CI failure returns to step 3 with the log excerpt; `attempts.py record` is called each time. After attempt 4 fails: step 7.
4. Review: dispatch a fresh `node-reviewer` with the brief, base, RED and head SHAs and the evidence. `request_changes` goes back to a new implementer (the budget applies). `test_spec_conflict` goes to step 7. Never edit a test to satisfy a reviewer; a wrong test needs a new RED from a new tester, and the human approves that.
5. Evidence: write `docs/status.yaml` entry and the PR body table (below); commit `docs(<ID>): gate evidence`.
6. Pull request: `gh pr create` as the bot. Body: summary; table `criterion | test or check | result | CI run link`; per slice the RED SHA, GREEN SHA, review verdict and reviewed SHA; the attempt log with models and the escalation if any; deviations and open questions; workflow-file changes called out (the human must push those with a workflow-scoped token, T-workflow-push-needs-pat). Post the `monolith-review` status only if every slice verdict is `approve` and the reviewed SHA equals the PR head (or later commits touch only `docs/status.yaml`): comment with verdicts, then `gh api repos/<owner>/<repo>/statuses/<sha> -f state=success -f context=monolith-review ...`. A later push needs a fresh review and status. Give the user the PR URL; the human merges.
7. Stop and ask: a false assumption in the node spec; an ambiguous or contradictory AC; a `TEST_SPEC_CONFLICT`; an exhausted retry budget; a needed change to SPEC, the graph, a node spec or protected paths. Propose the amendment as text; do not continue on a guess. Record SPEC defects in the node's `## Spec defects found`.
8. Next node (only if the operator asked for a run of nodes): fix CI on the open PR first (step 3 budget), then take the first node from `--ready`. A node whose dep is in an unmerged PR is not ready.

Retry rule, verbatim for the skill: at most three Sonnet attempts per slice, then one Opus attempt carrying all prior findings; then stop.

### Guard hook (`guard.py <role>`)
Reads the hook JSON on stdin, exits 2 with a reason on stderr to block. Roles: `tester`, `implementer`, `reviewer`, `session`.
- Path sets come from `tools/ci/policy.yaml`: `test_paths`, `protected_paths`. `ROLE_FORBIDDEN` = `protected_paths` plus `nodes/**`, `docs/status.yaml`, `docs/decisions/**`, `docs/study/**`, `LICENSE`. Role agents may edit workflows other than `verify.yml`, `discipline.yml`, `release*.yml` (a node such as B06 must write workflows); the orchestrator flags every `.github/` diff in the PR body.
- Tester: may edit only `test_paths` (and `slow_test_paths` for slow-only). Implementer: may not edit an existing file in `test_paths` (new ones are allowed); commit-time check rejects staged deletions inside test paths. Reviewer: edits nothing; no `git add/commit/checkout -b/stash`.
- All roles: no `gh`; no `git push|rebase|filter-branch|reset --hard|commit --amend|--no-verify`; shell writes into forbidden paths are detected by the same heuristic as strange-company (redirects, `cp mv tee rm sed -i`, `git checkout|apply|restore`, Python `open(...,'w')`), with the known limit that it is a heuristic. Stage with `git add` in one command and `git commit` in another, so the hook sees the index.
- Session role (every Claude session in the repo, from `settings.json`): block `gh pr merge|review`, `gh repo edit|delete|rename|archive`, `gh release create|delete|edit`, `gh secret|variable|ruleset`, `gh api ... /merge|/reviews|/protection|/rulesets`, any `--admin`; a posted commit status must have `context=monolith-review`; no push to the default branch name and no `--force`/`+ref` push; no identity tampering (`git config user.*`, `git -c user.name=`, `--author=`, `GIT_AUTHOR_*=` or `GIT_COMMITTER_*=` assignments in a commit command) — new relative to strange-company, from F04's identity rule; no credential persistence (`gh auth login|refresh|setup-git`, `git config credential`, tokens in remote URLs), because the PAT rule says a token is used transiently (inline `git -c credential.helper=...` is allowed) and never written to `.git/config`.
- Hook failures are visible: the guard prints the reason and the rule id; it never swallows its own errors (an exception exits 2 with the traceback, so a crash blocks rather than allows).

### Reviewer checklist (SPEC §3: "review checklist (F05)")
The reviewer prompt contains, verbatim, the SPEC §3 doctrine ids with a one-line check each, so a reviewer cannot approve silently past one: D-486-minimalism ("would this run on a 486 with a few MB of RAM? name the byte cost of every addition"), D-all-static, D-no-dynamic-loading-no-dlopen, D-no-python-on-target, D-bitmap-fonts-no-freetype, D-no-readding-removed-things, D-clock-origin-1970, D-486-tier-regime, D-static-musl-cross-all-the-way, D-supply-chain-honesty, D-tag-builds-from-source, D-revbump-on-overlay-change, D-hand-authored-rootfs-files-owned, D-state-and-no-hidden-stderr, D-two-epoch-pin-model. Plus: coverage of every AC by a test that asserts what the AC says; RED validity; frozen tests untouched; slow ACs have a green CI run link for the exact head; no unpinned input; `docs/system.yaml` updated; no `2>/dev/null` without `stderr-ok`.

## Gate
- **F05-AC-1** — `guard.py tester` allows edits to a path in `test_paths` and blocks any other (including a shell write by `tee` and `>`), while `implementer` blocks edits to an existing frozen test and allows a new test file and implementation paths. *Verify:* `tests/fast/agent-guard-paths.test.sh` (pipes hook JSON). *Tier:* fast.
- **F05-AC-2** — Every role is blocked from editing each `protected_paths` glob, `nodes/**`, `docs/status.yaml`, `docs/decisions/**` and `docs/study/**`, from the policy file; the guard's forbidden set is a superset of the policy's `protected_paths`, and a policy edit changes the guard behaviour. *Verify:* `tests/fast/agent-guard-protected.test.sh`. *Tier:* fast.
- **F05-AC-3** — Roles are blocked from `gh`, `git push`, `rebase`, `reset --hard`, `commit --amend` and `--no-verify`; the reviewer is blocked from `git add|commit|stash`; a `git commit` with `-a` or chained `git add` is blocked; a guard crash exits 2. *Verify:* `tests/fast/agent-guard-git.test.sh`. *Tier:* fast.
- **F05-AC-4** — The `session` role blocks `gh pr merge|review`, `gh repo edit`, `gh release create`, `gh secret`, `gh api .../merge`, `--admin`, force pushes, pushes to the default branch, and a status post whose context is not `monolith-review`; it allows `gh pr create` and `gh pr view`. *Verify:* `tests/fast/agent-guard-session.test.sh`. *Tier:* fast.
- **F05-AC-5** — The session role blocks credential persistence (`gh auth login`, `git config credential.*`, a token inside a remote URL) and allows an inline `git -c credential.helper=... push`. *Verify:* `tests/fast/agent-guard-creds.test.sh`. *Tier:* fast.
- **F05-AC-6** — The session role blocks `git config user.name|user.email`, `git -c user.name=...`, `git commit --author=...`, and `GIT_AUTHOR_NAME=`/`GIT_COMMITTER_EMAIL=` assignments inside a commit command. *Verify:* `tests/fast/agent-guard-identity.test.sh`. *Tier:* fast.
- **F05-AC-7** — `attempts.py check` prints `sonnet` for the first three attempts of a slice and `opus` for the fourth, exits 4 once four are recorded, keeps slices independent, and survives re-invocation (state in `out/node/<ID>/attempts.json`). *Verify:* `tests/fast/agent-attempts.test.sh`. *Tier:* fast.
- **F05-AC-8** — `brief.py F02` writes a brief whose AC lines are byte-identical to the spec's; it records whether a `decision:` is settled; it refuses an unknown node or AC id (exit 2). The skill text names `make test-fast`, `tools/agent/attempts.py`, "at most three Sonnet attempts, then one Opus", the evidence table in the PR body, slow-tier CI run links, `docs/status.yaml`, the rule that a human merges, and the recovery rule (reuse a green run's artifacts and logs; never rebuild to fix a publish or wrapper step). *Verify:* `tests/fast/agent-brief.test.sh`, `tests/fast/agent-skill-text.test.sh`. *Tier:* fast.
- **F05-AC-9** — The reviewer agent file contains every `D-*` id from SPEC §3, the read-only tool list (no `Edit`, `Write`), `model: opus`, and the verdict values `approve|request_changes|test_spec_conflict`; the tester and implementer files name `model: sonnet` and the `PreToolUse` hook with their own role. *Verify:* `tests/fast/agent-agents.test.sh`. *Tier:* fast.

## RED plan
Tests drive `guard.py` by piping hook JSON (`{"tool_name": ..., "tool_input": ...}`) and asserting exit code 0 or 2; they drive the tools in scratch repositories using F04's fixture helpers. Before implementation the guard and tools do not exist; the calls exit 2 or 127, an assertion failure under `t_assert_exit`. Slices: (1) guard path rules, AC-1, AC-2; (2) guard git, session, credentials and identity, AC-3 to AC-6; (3) tools, AC-7, AC-8 (tool half), AC-10; (4) agent and skill text, provenance, residue, AC-8 (text half), AC-9, AC-11, AC-12; (5) dry run and the live run, AC-13, AC-14. Text-content ACs are fast tests that grep the files for required phrases; they are weak evidence of quality, so the reviewer (a human for this node) reads the prompts. A roleplay check is not automatable.

## Risks and open questions
- Licensing. The copied files are AGPL-3.0-or-later in strange-company; this repo is MIT. Same copyright holder, but the files were largely written by `sc-agent-bot` under his direction. The owner should confirm in writing (a line in `PROVENANCE.md`) that relicensing is intended. If not, F05 must be rewritten clean-room instead of adapted.
- OD-4: bot name and noreply email are unknown. The guard and `agent-env.sh` read the policy, so one edit settles it.
- A cooperative-agent guard is bypassable (shell tricks). The real gate is F04; a false sense of security is the risk. The PR body must say this.
- Role agents may write workflow files, but only the human can push them (workflow scope). That makes B06-like nodes need a human push step; the orchestrator should plan for it, not discover it at the end (T-workflow-push-needs-pat).
- Retry limits are per slice; a node of 10 slices could still burn 40 attempts. A per-node cap is not set; the owner's call.
- MS1 is not enforced by the graph (see Spec defects). Until `--ready` refuses non-F nodes before F05 is done, nothing stops a node being built without the loop.
- Review quality: the reviewer is Opus, the implementer Sonnet. Whether Opus review catches what mechanical checks cannot is untested; AC-14 is the first evidence.

## Cost
Five slices, 14 ACs, size L. CI: about two fast-lane runs per slice. AC-14 needs one live run: a few agent invocations (Sonnet for tester and implementer, Opus for reviewer) and CI minutes, no build cycle. Token spend is the main cost and the retry budget bounds it per slice. No storage or hosting cost.
