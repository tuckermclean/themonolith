## Purpose
After this node the builder image can be rebuilt from inputs we hold, and a human can dispatch one workflow that moves `TOOLCHAIN_EPOCH`, re-derives `crossdev.lock` from the new inputs, rebuilds the builder image from mirrored inputs, and opens a PR whose checks include a full from-source build and the full oracle. The first use is not a bump: it rebuilds the image from the mirrored 20260810 stage3 and the 20260810 tree and compares the result with the adopted rc1 image (I03) against its declared tool list. That proves the adopted image is reproducible in kind, and it retires the digest that was copied by hand in Step 0. A toolchain bump changes the compiler and libc of every package, so it is never scheduled and never merged by automation.

## Scope
In:
- The first rebuild of the builder image (mode `first-rebuild`): mirror `gentoo/stage3:amd64-openrc-20260810` (still on Docker Hub; pin by digest) into our namespace, seed the 20260810 tree (I02), rebuild, and compare with I03's declared list.
- The Dockerfile rewrite that makes that rebuild possible: pinned `FROM`, tree from the store, pinned tools, crossdev inside the Dockerfile, no baked epoch variables, no baked tree.
- Dispatch-only workflow; target discovery for stage3 and toolchain tree; mirroring of the new inputs; `crossdev.lock` derivation from the new stage3 plus tree (no lag); builder image rebuild and push by digest; PR with a builder/toolchain delta report.
- A "from source, no cache" validation requirement, enforced by what the PR's checks run.
Out:
- The adopted image, its declared tool list, `inventory` and `declared-check`: I03 (this node reuses them on the rebuilt image). Image scan: S03.
- Tree fetch, verification, store: I02, I01.
- The routine `BUILD_EPOCH` path, PR helper conventions, token: M01.
- The PR build workflow and oracle jobs: B06, O02-O05.
- Staleness reporting for toolchain age: M04's pin-age report.

## Design

### Trigger
`workflow_dispatch` only, inputs `target_epoch` (`YYYYMMDD`, optional) and `mode` (`bump`, default, or `first-rebuild`: keep `TOOLCHAIN_EPOCH` at 20260810, rebuild the image from mirrored inputs and compare it with the adopted one). No `schedule`. Rejected: a scheduled bump; each run costs an image build (50-100 minutes per the predecessor's comments in `toolchain-bump.yml`) plus a cold build and the full oracle, and the result is consequential. Concurrency group `toolchain-bump`, no cancel. Token and bot identity as M01 (`BUMP_TOKEN`).

### Inputs and derivation
`pin-check toolchain [--target D]` finds the newest date that has all three upstream inputs: a stage3 for date D (the Docker Hub tag `gentoo/stage3:amd64-openrc-D`, or, for epochs after the first rebuild, the signed autobuild tarball `stage3-amd64-openrc-D*.tar.xz` named by `latest-stage3-amd64-openrc.txt`, a clearsigned file verified against `gentoo_key.release`), and a tree commit for the start of D (`snapshot commit-at D`T00:00:00Z`, I02). Missing any of them: exit 0 `action=noop` on HTTP 404, exit 1 on any other error, as in M01.

**Stage3 form.** The first rebuild pins the Docker Hub image by digest (`base_image.stage3: {image, tag, digest}`) and mirrors it with `oras cp` to `ghcr.io/tuckermclean/themonolith/stage3@<digest>`; the digest is unchanged by the copy, and the copy outlives Docker Hub's tag pruning. Docker Hub having dropped `gentoo/portage:20260811` shows the risk. Later epochs use the signed tarball (`base_image.stage3: {name, sha256, epoch}`), ingested by `builder-inputs stage3` (signature and sha256 verified, put as `sha256/<hex>` in class `distfile`), because a tarball is verified against Gentoo's key and a Docker Hub image is only as trustworthy as Docker Hub. That the Docker image equals the autobuild tarball plus trivial config is assumed, not verified; M02-AC-13's inventory comparison is the check. The mirror step needs `write:packages`, run transiently.

Ingest of the tree is I02's: `factory/bin/snapshot seed <commit>` (tree into the store), then read back the sha256 it prints. M02 calls it and records the result as `toolchain_tree` in the ledger.

`pin-apply toolchain NEW` is a scope-checking wrapper over I05's `pin set`. It sets `epochs.toolchain`, `base_image.stage3.*` and `toolchain_tree.{commit,sha256}`; it exits 1 if `pin diff` shows any other key changed (in particular `epochs.build`), if NEW is malformed or not newer, or a key is missing. `builder_image.{digest,inputs_hash}` are written by a second call, `pin-apply toolchain-image DIGEST INPUTS_HASH`, after the image build. Rejected: one combined write before the build, which would leave a PR with a digest of an image that never existed.

### `crossdev-lock-regen`
`factory/bin/crossdev-lock-regen --epoch E --out pins/crossdev.lock` runs in a throwaway container of the new `base_image.stage3` (not the builder image: it would lag) and calls `snapshot stage <commit> <dir>` (I02: the tree is extracted from the store, no network) and mounts it as `/var/db/repos/gentoo`, writes `*/* ~*` into `package.accept_keywords/zz-regen` so live `9999` ebuilds are excluded (T-live-ebuild-and-host-keyword-skew, the gcc-15.3.9999 incident), and queries `portageq best_visible / sys-libs/musl`, `=sys-devel/gcc-<major>*` (major from the current lock), and `sys-devel/binutils`.
- An empty or non-version answer for any of the three exits 1. The predecessor printed a warning and left the lock unchanged (`update-build-pins.sh:131-136`, T-crossdev-query-empty).
- The output header carries `# toolchain-epoch: <E>` (the line I05's `check-pins` requires), `# stage3: <digest or sha256>`, `# tree-commit: <40hex>` and the `*/* ~*` keyword rule, and no timestamp, so equal inputs give equal bytes.
- No `2>/dev/null` around `docker run` or `portageq`; stderr goes to the job log.
Rejected: querying the pre-bump builder image (the predecessor's `update_crossdev_lock`), which is why `crossdev.lock` lagged one epoch behind the pin it claims to serve.

### Image rebuild
After the lock regeneration, the job runs `factory/bin/builder-image build` and `push`. `push` publishes `<TOOLCHAIN_EPOCH>-<hash12>` on every invocation and writes `build/builder.digest`; `pin-apply toolchain-image` records the digest and `builder-image hash` in the ledger. Consumers pull by digest (T-builder-image-tag-not-pushed). If the build or push fails, no digest is written. `builder-image check-pin` (I03-AC-13) must then pass on the result.

**The Dockerfile rewrite (port first, each change forced by a criterion).** The starting point is I03's verbatim `image/Dockerfile`. Changes, each with its forcing criterion:
- `FROM gentoo/stage3:amd64-openrc-${TOOLCHAIN_EPOCH}` becomes `FROM` the mirrored stage3 by digest (first rebuild) or `FROM scratch` plus `ADD stage3.tar.xz` (later epochs): AC-14, AC-17.
- `emerge-webrsync --revert=…` (`Dockerfile:74`) becomes a `--network=none` bind mount of the tree staged from the store, used for the build and not left in the final image: AC-18.
- The syft and grype `curl | sh` loop (`:128-142`) and `sh.rustup.rs` (`:167-170`) are replaced by `image/install-tool` from `build/image-inputs/tools/` with sha256 from the ledger, and the rust nightly by rustup against a loopback mirror of stored dist components: AC-16, AC-21. (Whether rustup accepts a flat mirror laid out as `dist/<date>/…` is unverified; AC-21 settles it, fallback `rustup-init` offline from component tarballs.)
- The `docker run` plus `docker commit` crossdev step (`Makefile:295-325`) moves into the Dockerfile, so the build is one reproducible recipe with portage logs printed on failure; the stale `gcc-14.4.9999` mask (`Makefile:299`) is replaced by masks generated for `-9999` of musl, binutils, gcc and linux-headers: AC-19.
- `ARG BUILD_EPOCH` and `ENV SOURCE_DATE_EPOCH` are removed; `builder-image hash` covers `image/hash-inputs.txt` plus ledger values and excludes the build epoch and the runtime tree: AC-15.
- Labels `org.themonolith.inputs-hash`, `.toolchain-epoch` and `org.opencontainers.image.revision` are added: AC-20.
The libatomic fix (T-libatomic-static, `Dockerfile:191-202`) and the `-m32` check (`:55-64`) are kept as they are; I03's `image/checks/cross-toolchain.sh` and `host-tools.sh` run on the rebuilt image and a failure fails the job.

**Comparison with the adopted image (first rebuild).** The rebuilt image's `inventory` is checked by `declared-check` against I03's `image/host-tools.list`. The tool set must be equal. Versions are expected to equal the adopted image's because both used the 20260810 tree, and every difference is listed in the PR body. Bytes will differ (the build is not reproducible, see Risks). On a mismatch in the tool set the job fails and the adopted digest stays in the ledger.

### Pull request
Branch `pins/toolchain-OLD-NEW`. The commit changes `pins/pins.yaml`, `pins/crossdev.lock`, and nothing else. If `versions.lock` has entries tied to the toolchain (binutils is a world atom), the job runs R02's regeneration with the new builder and includes the result.

PR body: old and new `TOOLCHAIN_EPOCH`; stage3 digest or tarball sha256; toolchain tree commit and sha256; `crossdev.lock` diff (musl, gcc, binutils, linux-headers if present); old and new builder image digest; link to the S03 builder-image scan result for the new digest when it exists; a bold statement that this PR rebuilds every package. Labels `toolchain-bump`. The PR is opened normal, not draft, if the image built; draft with `needs-fixup` otherwise (same rule as M01).

### Validation: from source, full oracle
The PR's checks must, for a branch named `pins/toolchain-*`, run B06's build in release mode, which reads no cache (I06-AC-10), and the complete oracle (every mode of O02-O05 and O06). This is B06's and O02's trigger rule; M02 asserts it (M02-AC-8) and does not implement it. Rationale: a cached binpkg built by the old compiler would let a toolchain bump pass without exercising the new one. I06's global key contains the builder digest, so a new builder opens an empty cache namespace even without release mode; release mode is the explicit second guard.

The report job of M01 (`pin-bump-report.yml`) is generalised to also handle head branches starting `pins/toolchain-` and requires the full job list rather than the core list; M02 owns that change (it edits M01's file, in the same PR as the first toolchain-bump use).

### Time budget
Two separate jobs, never one: `rebuild-image` (timeout 180 minutes; the predecessor's crossdev plus host tools took 52 to 100+ minutes, exact figure unknown) and the PR checks (separate runs). The predecessor put image build and a 240-minute wait in one job with a 355-minute timeout; one slow run would hit the 360-minute hosted cap.

## Traps and doctrines preserved
- **D-two-epoch-pin-model:** a toolchain bump changes toolchain pins only. Prevented by M02-AC-2 (key scope) and M02-AC-9 (BUILD_EPOCH unchanged).
- **T-crossdev-query-empty:** empty query silently kept stale pins. Prevented by M02-AC-3.
- **One-cycle lag:** lock derived from the old image. Prevented by M02-AC-4 (lock header equals the pins it was derived from).
- **T-live-ebuild-and-host-keyword-skew:** `9999` ebuilds chosen. Prevented by M02-AC-5.
- **T-builder-image-tag-not-pushed:** consumers pull by digest; digest recorded only after push and `check-pin`. Prevented by M02-AC-6.
- **T-libatomic-static / T-resolved-kernel-config-vacuous:** a new gcc can drop a fix or change the resolved kernel config. Prevented by M02-AC-8 (full oracle, including O06 and the resolved-config checks of B02, runs on the PR).
- **Mirrored inputs (SPEC §2.2):** the build reads the tree from the store. Prevented by M02-AC-7. The stage3 and tool binaries are mirrored too: M02-AC-16, AC-17.
- **Adopted image is real (I03):** the first rebuild must reproduce the declared tool set. Prevented by M02-AC-13.
- **Offline rebuild (was I04-AC-14):** the image rebuilds with host-tool and crossdev distfiles served only from the mirror. Prevented by M02-AC-22.
- **SPEC §8 Humans merge:** M01-AC-1's grep covers this workflow; M02-AC-10 asserts it names `toolchain-bump.yml`.

## Risks and open questions
- Hardest: the builder image is not bit-reproducible, so each rebuild yields a new digest even for equal inputs; the digest in the PR is whatever the single build produced. The PR must be merged with that digest or the build repeated. Accept: digest is evidence, not an input hash.
- Stage3 comes from Gentoo autobuilds at bump time (or, for the first rebuild, Docker Hub by digest); `builder-inputs stage3` verifies signature and sha256 for tarballs, and M02 fails if the ingest tool does. If Docker Hub has already dropped `amd64-openrc-20260810` the first rebuild cannot start from the image form; the signed tarball of that date is the fallback if autobuilds still holds it (unverified).
- The first rebuild may not reproduce the adopted tool set: the rc1 image came out of `docker commit` and its tree was fetched by `emerge-webrsync` on 2026-08-10 or later, and the commit chosen by `commit-at` is only near it. A mismatch is a finding, recorded, and the adopted digest stays the pin.
- A toolchain bump can break `emerge` for reasons unrelated to the toolchain (new ebuild versions, T-glib-docutils-eigen-live). The fixup loop is human work; the PR cannot be auto-fixed.
- `crossdev.lock` today holds musl and gcc only (`crossdev.lock:8-9`); binutils and kernel headers come from `versions.lock` (I03 `crossdev` call). M02 therefore writes musl and gcc into the lock and leaves binutils to R02's regeneration, which M02 triggers.
- Cost of the full oracle on every toolchain bump is intentional; if the owner wants a cheaper path, relax M02-AC-8 explicitly.

## Cost
Seven agent slices: (0) Dockerfile rewrite, hash, install-tool, stage3 and rust ingest (AC-14 to AC-18, AC-21); (0b) first rebuild job and comparison (AC-13, AC-19, AC-20, AC-22); (1) `pin-check toolchain`, `pin-apply toolchain`, tests; (2) `crossdev-lock-regen` and tests; (3) workflow and failure-injection tests; (4) docs plus generalising M01's report job. CI: the first rebuild is an image build of 1 to 2 hours, run two or three times while the Dockerfile rewrite is fixed. The one real dispatch at acceptance is an image build (about 1-2 hours) plus a cold from-source build (30-60 minutes) plus the full oracle: roughly three to four hours of runner time, three CI cycles counting one fixup. Each later bump costs the same. Store: one new stage3 digest (if mirrored) and one builder image per bump, kept forever when referenced by a tag (M03).

- SPEC §6 says the stage3 is "the stage3 tarball (sha256 of the signed autobuild, I03)". The first rebuild pins the Docker Hub image `gentoo/stage3:amd64-openrc-20260810` by digest and mirrors it (this node); the signed tarball is for later epochs. SPEC §6 should name M02 and both forms.

- This node absorbs work that v0.2 gave to I03 (Dockerfile rewrite, ingest, push) and I04 (offline image rebuild); M02 is `deferred` in graph.yaml, so nothing on the path to MS2 may depend on those. B01 and B06 must pull the builder by digest only (I03).
