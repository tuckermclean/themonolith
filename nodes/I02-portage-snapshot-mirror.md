## Purpose
After this node a Gentoo portage snapshot is ingested once from upstream, GPG-verified, and kept in the store forever; every build reads its pinned epoch only from the store and feeds it to `emerge-webrsync` over a loopback HTTP server with no upstream in `GENTOO_MIRRORS`. A missing or corrupt pin fails loudly. The predecessor's snapshot mirror lived in the dead S3 account, and its pinned epoch (20260811) is no longer fetchable upstream, so this node also defines how the first epoch of the new repository is chosen and seeded.

## Scope
In:
- Ingest: fetch `gentoo-<epoch>.tar.xz` and `.gpgsig` from upstream, verify, `store put snapshot`.
- `import` of a snapshot obtained elsewhere (OD-6 rescue, offline mirrors) with the same verification.
- `stage`: store to a local directory, plus a locally generated `.md5sum`.
- `webrsync`: serve that directory on `127.0.0.1` and run `emerge-webrsync --revert=<epoch>`, no upstream.
- `latest`: resolve the newest upstream date that has both files.
- The seeding workflow for the first epochs.

Out:
- Which epoch is current and bumping it: I05 (ledger), M01 (BUILD_EPOCH bumps), M02 (TOOLCHAIN_EPOCH bumps).
- Baking the toolchain tree into the builder image and the stage3 tarball: I03.
- Merging the bumped epoch into a build and the `package.mask` mirroring to the host: B01.
- Retention of snapshots: M03 (forever).
- Store backends: F06, I01.

## Design
**Store keys (SPEC §5).** Class `snapshot`: `gentoo-<epoch>.tar.xz` and `gentoo-<epoch>.tar.xz.gpgsig`. `<epoch>` matches `^[0-9]{8}$`, is a real calendar date, and is not in the future (UTC). The `.md5sum` is not stored: `stage` generates it from the verified tarball (`md5sum` output format, file name only). Rejected: storing the upstream `.md5sum`; GPG is authoritative and the md5 file is optional in the predecessor (`sync-portage.sh:57,71`).

**GPG verification.** `factory/lib/gpgverify.sh verify <sig> <file> <keyfile> <fingerprint>` imports the key into a throwaway `GNUPGHOME`, checks that the keyring contains exactly the pinned fingerprint (the predecessor recorded `DCD05B71EAB94199527F44ACDB6B8C1F96D8BF6D` as the snapshot signing key, `Dockerfile:68-69`; confirm against Gentoo's published key list when pinning), runs `gpg --status-fd` and accepts only `VALIDSIG <that fingerprint>`. Expired, revoked, wrong-signer and missing-signature results are all failures. Verification happens twice: at ingest (this tool) and at use (`emerge-webrsync` with `FEATURES=webrsync-gpg` set explicitly; whether stage3 enables it by default is unknown). The use-time check protects against a tampered store.

**Subcommands** (POSIX sh; diagnostics to stderr; only `latest` prints to stdout):
- `snapshot latest` — list `${SNAPSHOT_UPSTREAM:-https://distfiles.gentoo.org/snapshots}/`, pick the newest date for which both `.tar.xz` and `.gpgsig` exist (HEAD both); print `YYYYMMDD`.
- `snapshot seed <epoch|latest>` — `store has`; if present, fetch nothing and confirm the stored tarball verifies (exit 0). Otherwise download to a temp dir, reject empty files, verify, `store put` both. If the store holds the epoch with a different body than upstream now serves (upstream re-rolls the daily file), exit 4, keep ours, name both sha256 values.
- `snapshot import <epoch> <tarball> <sig>` — verify, then `store put`; the OD-6 rescue path (`aws s3 cp` the old object by hand, then `import`).
- `snapshot stage <epoch> <dir> [--sha256 <hex>]` — `store get` both files into `<dir>/snapshots/`, re-verify the signature, check the optional pinned sha256 (from the ledger), write `.md5sum`. A missing store object exits 3 with a message naming the epoch and the key. Never touches upstream; a stub `wget`/`curl` on `PATH` that is called fails the test.
- `snapshot webrsync <epoch> <dir>` — runs inside the builder (needs `emerge-webrsync`, `python3`, `wget`). Serve `<dir>` with `python3 -m http.server <port> --bind 127.0.0.1`, wait up to 10 s until `snapshots/gentoo-<epoch>.tar.xz.gpgsig` answers (else exit 1, no webrsync call), then run `GENTOO_MIRRORS=http://127.0.0.1:<port> FEATURES="${FEATURES} webrsync-gpg" emerge-webrsync --revert=<epoch>`. A trap kills the server on exit. Default port 8899 (`SNAPSHOT_HTTP_PORT`).
Host-side commands need the store credentials; the in-container command needs none. The tarball is passed to the container as a read-only bind mount.

**Why http on loopback (invariant carried).** `emerge-webrsync` cannot read `file://` mirrors and silently falls back to `distfiles.gentoo.org`, whose daily snapshot is re-rolled; that made the tree drift and voided the whole binpkg cache (`sync-portage.sh:8-17`). `GENTOO_MIRRORS` must contain exactly the loopback URL. Test case 6 of the predecessor is ported unchanged in intent.

**Choosing and seeding the first epochs.** Upstream keeps only recent dailies, and 20260810 and 20260811 are already gone (404). The repository therefore starts from a fresh pair, chosen by the owner at seed time:
1. `TOOLCHAIN_EPOCH` = the newest date that has both a published stage3 build (I03 resolves this) and a snapshot, and `BUILD_EPOCH` = `snapshot latest` at seed time. They may be equal on day one.
2. The `seed-inputs.yml` dispatch workflow runs `snapshot seed` for each, prints the sha256 of both tarballs, and opens no PR itself. The owner (or I05's `pin set`) writes the epochs and sha256 values into `pins/pins.yaml` (protected path).
3. If OD-6 is answered "recoverable", `import` the old 20260811 (and 20260810) objects too; they are then ordinary epochs and rc1 becomes reproducible. Default: treat as lost.

**Toolchain tree sourcing (decision).** The toolchain tree baked into the builder (I03) is a second snapshot of this same class, seeded and verified the same way, not an image.
Rejected: pinning the `gentoo/portage:<date>` Docker image by digest. It is not a webrsync tarball, so `--revert` cannot use it, it carries no Gentoo signature (trust would be Docker Hub's), and Docker Hub already dropped `gentoo/portage:20260811`.

**Failure behaviour.** There is no fallback chain. If the pinned epoch is absent from the store, `stage` exits 3 with "epoch <E> not in store: run seed-inputs (or import)". If `--sha256` is supplied and differs, exit 5. If the epoch variable is empty, exit 2.

## Traps and doctrines preserved
- **T-portage-snapshot-fetch** (file:// fallback to a drifting upstream; pruning outage): AC-5, AC-7, AC-8. Verification must survive the move off S3: AC-1, AC-2, AC-3.
- **D-two-epoch-pin-model** (two independent epochs; a BUILD_EPOCH bump never forces a toolchain rebuild): the snapshot is parameterised by epoch only, with no coupling to the image: AC-5; ledger checks in I05.
- **Principle 2** (inputs mirrored): AC-11.
- **T-pin-bump-false-green** (a bump validated against a snapshot that was not actually available): `seed` is the only way a snapshot enters; M01 must call `store has`. AC-10 gives M01 a single yes/no query.
- **D-state-and-no-hidden-stderr**: AC-9.

## Gate
- **I02-AC-1** — `seed` with a correctly signed tarball (throwaway key) puts both objects into an `fs` store; `store get` returns byte-identical files. *Verify:* `tests/fast/snapshot-seed.test.sh` case `good`. *Tier:* fast.
- **I02-AC-2** — `seed` and `import` reject, and put nothing for: a bad signature, a signature by a different key, a keyring whose fingerprint differs from the pin, a missing `.gpgsig`, a zero-byte tarball. *Verify:* `tests/fast/snapshot-seed.test.sh` cases `bad-sig`, `wrong-signer`, `wrong-fingerprint`, `no-sig`, `empty`. *Tier:* fast.
- **I02-AC-3** — Re-seeding an epoch whose stored body equals upstream exits 0 and uploads nothing; a re-rolled upstream body exits 4, leaves the stored object unchanged and prints both sha256 values. *Verify:* `tests/fast/snapshot-seed.test.sh` cases `idempotent`, `reroll`. *Tier:* fast.
- **I02-AC-4** — `latest` returns the newest date for which both files exist, ignores a newer date with only the tarball, and prints nothing else to stdout. *Verify:* `tests/fast/snapshot-seed.test.sh` case `latest` against a local HTTP fixture via `SNAPSHOT_UPSTREAM`. *Tier:* fast.
- **I02-AC-5** — `stage` reads only from the store: with `wget` and `curl` stubs on `PATH` that fail the test when called, a present epoch stages and an absent epoch exits 3 naming the epoch and key. *Verify:* `tests/fast/snapshot-stage.test.sh`. *Tier:* fast.
- **I02-AC-6** — `stage --sha256` with a wrong value exits 5 and leaves no staged files; `stage` regenerates `.md5sum` and re-verifies the signature (a tampered store object exits non-zero). *Verify:* `tests/fast/snapshot-stage.test.sh` cases `pin-mismatch`, `tampered-store`. *Tier:* fast.
- **I02-AC-7** — `webrsync` runs `emerge-webrsync` with `GENTOO_MIRRORS` exactly `http://127.0.0.1:<port>` (no other URL, no `gentoo.org` anywhere in the call log) and `--revert=<epoch>`, with `FEATURES` containing `webrsync-gpg`. *Verify:* `tests/fast/snapshot-webrsync.test.sh` (port of predecessor case 6, plus the FEATURES assertion). *Tier:* fast.
- **I02-AC-8** — If the loopback server never answers, `webrsync` exits non-zero within 15 s without calling `emerge-webrsync`; on every exit path the server process is gone. *Verify:* `tests/fast/snapshot-webrsync.test.sh` cases `never-ready`, `cleanup`. *Tier:* fast.
- **I02-AC-9** — `factory/bin/snapshot` and `factory/lib/gpgverify.sh` pass shellcheck and contain no `2>/dev/null`, no `|| true` and no `-q` on a command whose failure decides the result, except lines annotated `# allow-silent: <reason>`. *Verify:* F01 lint plus `tests/fast/snapshot-seed.test.sh` case `lint`. *Tier:* fast.
- **I02-AC-10** — `snapshot stage <epoch> --check` (no directory; equivalent to `store has snapshot gentoo-<epoch>.tar.xz`) is the single presence query: exits 0 present, 3 absent, other non-zero on store errors (auth/network are never "absent"). *Verify:* `tests/fast/snapshot-stage.test.sh` case `check`. *Tier:* fast.
- **I02-AC-11** — The `seed-inputs` workflow, run against real upstream with the real pinned key, seeds the current `latest` epoch into the real store and `snapshot stage` of it succeeds in a fresh runner; this also proves the pinned key still validates real current signatures. *Verify:* CI run of `seed-inputs.yml` (dispatch), link recorded in the PR table. *Tier:* slow.
- **I02-AC-12** — `emerge-webrsync` accepts the staged directory (no `.md5sum` fetched from upstream, signature checked) and produces `/var/db/repos/gentoo`. *Verify:* I03-AC-7 (needs the builder image; this node cannot run it earlier). *Tier:* slow.

## Risks and open questions
- Snapshot size is unmeasured. Estimate 40 to 60 MB per tarball (not verified); one new epoch per week would be about 2 to 3 GB per year in a forever class. Decide on thinning (keep release epochs only) with M03.
- The Gentoo snapshot signing key is rotated on a schedule; the pinned key file can go stale. AC-11 is the early warning; the key refresh is an I05 pin bump (M04).
- Unknown whether `emerge-webrsync` works without the upstream `.md5sum` when `webrsync-gpg` is on. The predecessor's test treats `.md5sum` as optional only at fetch level. AC-12 settles it; fallback is already in the design (local `.md5sum`).
- Upstream may re-roll a daily file after we ingest it (the predecessor saw drift). We keep ours (AC-3); if the owner prefers to follow upstream the epoch must be re-pinned, not overwritten.
- OD-6: rescuing 20260811 is possible only if the AWS account is recoverable. Not required for anything except rc1 reproducibility and O07's baseline narrative.
- What happens if the first-epoch choice lands on a day when stage3 and snapshot dates disagree: resolved in I03 (`TOOLCHAIN_EPOCH` needs both).

## Cost
Two slices: (1) gpgverify, `seed`, `import`, `latest`, AC-1 to AC-4, AC-9; (2) `stage`, `webrsync`, workflow, AC-5 to AC-8, AC-10, AC-11. AC-12 is delivered by I03. CI cycles: two short runs plus one seeding dispatch. Money: about 50 MB of store per epoch (estimate), seeding two epochs initially.

## Spec defects found
- graph.yaml gives I02 only a dependency on I01, but the signature check needs the pinned key and fingerprint, which SPEC §6 places in `pins/pins.yaml` (I05, which comes later). Resolution here: I02 ships `pins/keys/gentoo-snapshot.asc` and takes fingerprint from `pins.yaml: gentoo_key` in the I05 format, with a command-line override used by the fast tests.
- SPEC §5 lists the snapshot class as `gentoo-<epoch>.tar.xz[.gpgsig]` only; a manifest of when and from where the file was ingested is not kept. Provenance is carried by the pinned sha256 in the ledger instead.
