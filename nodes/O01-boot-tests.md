## Purpose
After this node the predecessor's 17 boot modes run in CI against any ISO, whether it came from this repository's build or from a URL. The rc1 lane runs them on `v0.1.0-rc1` before this repository builds anything. Every mode passes on the rc1 ISO.

## Standard mechanism
QEMU, OVMF and `pexpect` on a GitHub-hosted runner, as the predecessor. openQA was considered (SPEC §5): it is a service to run for 17 serial-console modes. No gap is recorded and no custom code is added. The harness is carried as it is: the milestone strings, the ISOLINUX `serial` label, the GRUB `(serial)` entry (SPEC §7), the sentinel protocol and the launch-retry rule.

## Changes from the port
1. **Reusable workflow takes the ISO by artifact or by URL.** The predecessor's only input is `build-version`, and every job restores the ISO with `actions/cache/restore` keyed on the run id (`boot-test.yml:23-26,80-85`). Inputs become `iso-artifact` (an Actions artifact name) or `iso-url` plus `iso-sha256`, and optional `kernel-version` and `modes` (a list; default all 17, so a caller can leave out a mode whose package is not on the disc). A `fetch-iso` job downloads and `sha256sum -c`-verifies a URL ISO, then uploads it as an artifact; in artifact mode it does nothing. Every mode job uses `actions/download-artifact`. Reason: SPEC §4.1 forbids `actions/cache` between jobs, and the rc1 lane needs a URL. Proved by AC-2, AC-4.
2. **`boot-test-rc1.yml`** calls the workflow with the rc1 release URL, sha256 `a96006596b13cc09fa951f54aadc0b816765d783e5d0e40895d7d0945edeb27a` and kernel version `6.12.80-i486-monolith` (from `versions.lock:8` and `kernel.config:36` at b9f533b; not yet checked against the ISO). Proved by AC-4.
3. **Tools come from the pinned toolbox.** The 17 `pip install pexpect` steps (for example `boot-test.yml:77-78`) and any `apt-get` install of QEMU or OVMF on the runner are removed. Each mode job runs `make test-boot` with its mode (and RAM size or device model where the matrix sets one), and the target runs `boot-test.py` through `toolbox/run`, where QEMU, OVMF and pexpect are pinned by `toolbox/Containerfile`. Proved by AC-2, AC-7.
4. **QEMU and OVMF versions are recorded.** `make test-boot` writes `qemu-system-i386 --version`, `qemu-system-x86_64 --version` and `dpkg-query -W qemu-system-x86 ovmf`, run inside the toolbox, to `output/tool-versions.txt`, which each job uploads with the serial log. Reason: SPEC §6 needs the QEMU version in `release-inputs.json`. Proved by AC-5.
5. **`expected-kernel` fails on an empty result.** Today an empty `KVER` or `LOCALVERSION` gives `--kernel-version ""`, and `smoke_kernel_version` passes trivially (oracle.yaml `ci.boot-test.expected-kernel`). The step adds `test -n` guards and uses the `kernel-version` input when given. The computing step reads `CONFIG_LOCALVERSION` from the savedconfig path B02 defines (`configs/portage/savedconfig/sys-kernel/monolith-kernel`; B02's test rejects the old one). Until B01 and B02 have ported the kernel config, only the `kernel-version` input works, and the guard fails loudly without it. Proved by AC-2.
6. **Action references are full commit SHAs** (SPEC §6). F01's standing test requires it, so this file is pinned as it is ported; AC-2 keeps it true.
7. **clock-epoch stale text removed.** The module docstring (`boot-test.py:36-42`) says clock-epoch uses a fixture server and checks that the hook corrects the clock. `run_clock_epoch` (`:543-585`) tests the opposite (flag raised, clock left at 1970, `-nic none`), and the workflow still starts an `http.server` the guest can never reach (`boot-test.yml:796-805`). The docstring is corrected and the dead start and stop steps of the `clock-epoch` job are deleted (`nat-router`'s are live and stay). The correction path stays covered by `scripts/tests/monolith-time.test.sh`; no new mode is added. Proved by AC-2.
8. **S3/AWS:** `boot-test.yml` and `boot-test.py` contain no S3 or AWS reference (checked by grep), so nothing is removed here. I01 owns the repository-wide removal; AC-2 keeps it true for this file.
9. **Manual boots.** The predecessor's `make test` (`Makefile:500`, an interactive BIOS boot in QEMU with `-cpu 486 -m 64M`) and `make test-uefi` come in as `run-bios` and `run-uefi`: they are not tests, and `make test` and the `test-*` targets run tests (F01, SPEC §7). *AC-6.*
10. **`make test-boot`.** Part of `make test`. It boots `ISO` in every mode, or in `MODE=` alone, through `boot-test.py` in the toolbox. Until B03 builds an ISO, the default `ISO` is rc1's, fetched and checked against its sha256 as a Make prerequisite (SPEC §7, rc1 lane); B03 makes the built ISO the default. *AC-7.*
11. **The shell-ready probe waits for the shell, not the tty's echo.** `wait_for_shell` (`boot-test.py:810-841`) sends `echo MONOLITH_SHELL_READY_<id>` and matches the marker, but the serial tty echoes the typed line at once, before any shell reads it. The probe then passes while the console stub is still at its "press Enter" prompt, and the first check is swallowed or reads the banner: `uname -r` timed out in `uefi` three times locally, and `cirrus coldplug` read the motd in `vga` twice in CI (run 41026572862). This is the "serial warmup" race the Risks list. The probe's output now differs from its typed text (an arithmetic expansion, for example `echo MONOLITH_SHELL_READY_<id>_$((6*7))` matched as `…_42`), so only an executed echo matches. Nothing else in the harness changes. *AC-8.*

## Gate
- **O01-AC-1** — `boot-test.py`'s `should_retry_launch` relaunches a guest that never reached `/init` while attempts remain, stops on the last attempt and reports the failure, and never relaunches after a success or after a failure that came once `/init` was reached. The module imports with `pexpect` stubbed, without running a boot. *Verify:* `scripts/tests/boot-test-retry.test.sh`.
- **O01-AC-2** — `boot-test.yml` is a `workflow_call` with the inputs of change 1; has no `actions/cache`, `aws` or `s3` text and no `http.server` in the `clock-epoch` job (`nat-router` keeps its own, which the guest does reach); uses only SHA-pinned actions; has no `pip`, `apt-get` or `setup-*` step, and each mode job's test step is `make test-boot` with its mode; and its `expected-kernel` step has a `test -n` guard. *Verify:* `bash scripts/tests/boot-test-workflow.test.sh`.
- **O01-AC-3** — `boot-test.py` still has the six `-cpu 486` argument pairs of b9f533b and `MODE_DEFAULT_RAM["bios"] == 64`; the workflow keeps `ram_mb: [64, 256]`. *Verify:* `bash scripts/tests/boot-test-workflow.test.sh`.
- **O01-AC-4** — `boot-test-rc1.yml` runs all 17 modes (bios at 64 and 256 MB, and the nic and vga model loops) on the rc1 ISO fetched by URL and sha256, and every job is green. A wrong `iso-sha256` fails the `fetch-iso` job before any mode runs. *Verify:* workflow_dispatch of `boot-test-rc1.yml`, once with the right and once with a wrong digest.
- **O01-AC-5** — Each mode job's uploaded artifact contains `tool-versions.txt` with the QEMU version lines and the `ovmf` package version. *Verify:* download an artifact from the AC-4 run and `grep -c 'QEMU emulator version'`.
- **O01-AC-6** — `make -n run-bios` runs `qemu-system-i386` with `-cpu 486` and `-m 64M` on the ISO, and `make -n run-uefi` runs `qemu-system-x86_64` with OVMF. *Verify:* `scripts/tests/boot-test-workflow.test.sh`.
- **O01-AC-7** — `make test` depends on `test-boot`. `make -n test-boot` runs `boot-test.py` through `toolbox/run` once per mode on the default `ISO`, which until B03 is rc1's ISO behind a sha256 check; `MODE=bios` runs only that mode, and a wrong sha256 fails before any boot. *Verify:* `scripts/tests/boot-test-workflow.test.sh`; `make test-boot ISO=<rc1 ISO>` locally, log under `out/node/O01/`.
- **O01-AC-8** — `wait_for_shell` returns only once the guest shell has executed its probe: against a fake console that echoes typed input at once but runs it only after a delay, it does not return on the echo, and the next command's output is not mixed with what came before. *Verify:* `scripts/tests/boot-test-shell.test.sh` (pexpect-free fake child).

## Risks
- Measured in the predecessor: modes take about 1–2 minutes each, `nic-models` 9.1 minutes, about 10 minutes wall in parallel. Not re-measured here.
- Artifact mode (`iso-artifact`) has no caller until B03; its first proof is B03's build. The URL path is proved here.
- The ISO's kernel version string for the rc1 caller is derived from predecessor files, not from the ISO. A mismatch would fail `uname -r` in every mode at the first run.
- The toolbox pins QEMU and OVMF by Debian snapshot date; a runner image update no longer changes them. Whether TCG on the runner boots each mode within the predecessor's timeouts is unverified until the first CI run.
- Not done here: golden screendumps, second-child retry attribution, and modes beyond the predecessor's. They would change behaviour without a demonstrated failure.
