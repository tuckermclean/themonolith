## Purpose
Today every tag fails the CVE gate: the built ISO has thousands of gating findings, most of them the kernel matched by CPE against NVD (S01 Risks), and on a tag `make test-gates` fails the attestation job on them (`Makefile:702`). So no tag can publish, `v0.2.0-alpha1` included.

After this node a pre-release tag (`vX.Y.Z-<suffix>`: `-alpha…`, `-beta…`, `-rc…`) treats the CVE gate as `main` does. The verdict is recorded and reported, and it does not fail the attestation job. Every other gate and check still blocks. A final tag (`vX.Y.Z`, no suffix) still fails on CVEs. The release notes state the CVE verdict and its counts, as `attestation-summary.json` and the dashboard already do, so an alpha says plainly that it ships with known CVEs.

## Standard mechanism
None needed. The report-only mode exists: `gates-verdict.sh --cve-report-only` (S01 change 9) lets the licence, unowned and SBOM gates and the grype DB record decide and only reports the CVE verdict, and `test-gates` selects it with `CVE_REPORT_ONLY=1` (B03 change 13). The pre-release rule exists in `release-create.sh:10-16` (a hyphen after `v` is a prerelease). This node moves that rule into one script that both read, and lets `test-gates` select the existing mode on a pre-release tag. GitHub Actions sets `GITHUB_REF_TYPE` and `GITHUB_REF_NAME` on every run, so `build.yml` does not change: the decision lives in Make and `scripts/`, not in workflow YAML (SPEC §7).

## Changes from the port
1. **One pre-release rule.** `scripts/release-kind.sh <tag>` prints `prerelease` for a `v` tag with a suffix after `vX.Y.Z` and `final` for `vX.Y.Z`. It is the rule `release-create.sh:10-16` applies today: any hyphen after the leading `v`. It exits non-zero, naming the tag, for anything else (empty, no leading `v`). Its rule is a `case` on the tag without its `v`, with a `*-*` branch. `release-create.sh` takes its `--prerelease --latest=false` decision from it, with the same two `==>` lines: it runs `$RELEASE_KIND`, which defaults to the `release-kind.sh` next to `release-create.sh`, so a direct run (P04-AC-7) still works. The `release-create` recipe passes `RELEASE_KIND='scripts/release-kind.sh'` beside `RELEASE_DIR`, so `make -n release-create` names `scripts/release-kind.sh`. P01-AC-9's one-level read of the scripts that output names then still finds `--prerelease` and `--latest=false` (in `release-create.sh`) and `*-*` (in `release-kind.sh`), and no frozen line changes. *AC-1.*
2. **`test-gates` on a tag.** When `GITHUB_REF_TYPE` is `tag` and `release-kind.sh "$GITHUB_REF_NAME"` prints `prerelease`, `test-gates` runs as it does with `CVE_REPORT_ONLY=1`: `gates-verdict.sh --cve-report-only`, with no `arc -eq 0` requirement. It first prints `test-gates: pre-release tag <tag>: the CVE verdict is reported, not gating`. On a final tag, and with `GITHUB_REF_TYPE` unset or `branch`, the recipe is what it is today: `CVE_REPORT_ONLY` alone decides. The rc1 branch (`--rc1`, the SBOM diff) does not change. A tag that `release-kind.sh` rejects fails `test-gates`. *AC-2, AC-3.*
3. **Release notes.** `release-notes.sh` reads the release's `attestation-summary.json` (`$RELEASE_DIR/attestation-summary.json`, which `release-assets` copies and the release publishes). `RELEASE_DIR` comes from the `release-notes` recipe, which passes `RELEASE_DIR='$(RELEASE_DIR)'` as `release-create` does (the Makefile's `RELEASE_DIR ?= output/release`), so release.yml's "Assemble the release notes" step does not change; the script requires `RELEASE_DIR` and has no default of its own. It adds a `### Supply-chain gates` section. It gives the CVE verdict (`cve_check`), the number of gating findings, the waived findings and the total from `cve_coverage` (`gating_findings`, `waived_findings`, `total_findings`), the grype DB build time, and the licence and unowned verdicts. For a pre-release whose `cve_check` is `fail`, it adds one sentence: this pre-release ships with known CVE findings, listed in `attestation-summary.json`, and a final release must clear them. A missing or unparseable summary fails the step, naming the file. The gating count is the gate's own: `check-cves.sh` writes it as `summary.gating_findings` in `cve-report-coverage.json` (the findings `gates-verdict.sh` counts), and `attestation.sh` copies it into `cve_coverage.gating_findings`. It is not the length of `cve_failures`, which lists every grype match, waived and below-threshold ones included. *AC-4.*
4. **Docs.** The `Prerelease / RC tags` section of `docs/releasing.md` (`:38-46`) says that on a pre-release tag the CVE gate reports and does not block, which other gates and checks still block, where the verdict is published, and that a final tag must pass it. It also covers `-alpha` tags, which the section does not name today. *AC-6.*

## Risks
- **What an alpha ships with.** An alpha is published with thousands of known CVE findings until the gate is made passable (issue #117 part 2). This is the owner's choice, stated in the issue. It is visible in the notes, the summary and the dashboard, and it is never Latest.
- **Old tags stay broken.** `v0.2.0-alpha1` points at `8c1b68a`. Re-running its Build run uses that commit's workflow and Makefile, so it fails again. The alpha needs a new tag on a commit that contains this node.
- **`GITHUB_REF_NAME` outside Actions.** A local `make test-gates` has no `GITHUB_REF_TYPE`, so it keeps today's behaviour. A caller that sets `GITHUB_REF_TYPE=tag` by hand gets the tag rule.
- **Other open work on the same files.** The node planned for issue #115's release path (spec PR #116, not merged) also edits `release-create.sh` and `docs/releasing.md`. Whichever lands second merges around the other: change 1 touches only the `case`, and change 4 touches only the pre-release section.
