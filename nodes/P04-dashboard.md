## Purpose
After this node the advisory feed's GitHub Pages site under the OD-1 name is also the project's public face. `/` lists every release, this repository's and the predecessor's `v0.1.0-rc1`, and `/<tag>/` shows one release: the gates it passed, its current advisory status, its packages and licences, its unowned files, its assets and the command that verifies it. A revoked build's `details_url` (`<OD-1 URL>/<tag>`, P03) lands on that page. The pages are static HTML written at publish time, need no JavaScript, and read in the disc's own browser.

## Standard mechanism
- **Hosting:** GitHub Pages, the site P03 already deploys. `actions/deploy-pages` replaces the whole site on every deploy, so the pages are written by the same `advisory-feed.yml` run that writes `status/`, into the same tree. `/status/` is unchanged.
- **Data:** GitHub Releases through `gh` (`gh release list`, `gh release view --json`, `gh release download`), the SBOMs the feed run already downloads, and the status files it writes. A browser cannot read release assets directly (GitHub sends no CORS headers on them), so the data is read at publish time, not in the page.
- **Generator:** Python 3 with its standard library (`html.escape`, string templates), the host-side language of SPEC §4.4. A static-site generator was considered: Jekyll is bypassed by an artifact deploy and Hugo is a build toolchain, and neither is needed for two page types.
- **Gap and exception.** A GitHub release page shows assets and notes, not the gate results, the advisory status or the SBOM's contents. This node writes new code rather than porting the predecessor's `web/` app: a deliberate exception to SPEC §2.2, chosen by the owner. The benefit: no runtime fetches, no third-party fonts or CDNs, and pages readable without JavaScript in the disc's own browser.

## Changes from the port
1. **Each release publishes its gate summary.** `make release-assets` copies `attestation-summary.json` (written by S01's `attestation.sh` in the attestation job) into the release directory, `release-sums.sh` lists it in `SHA256SUMS` before signing, the build job's reports upload carries it, and `release-create.sh` uploads it. P01's release tests keep passing. Proved by AC-7.
2. **The generator.** `make dashboard` runs `dashboard.py` in the toolbox after `make advisory-feed`. It reads `output/advisory-feed/data/<tag>/bom.cdx.json` and `output/advisory-feed/site/status/<tag>.json`, downloads each release's metadata, `SHA256SUMS` and `attestation-summary.json` (rc1's from the predecessor release), and writes `index.html`, `<tag>/index.html` and `style.css` into `output/advisory-feed/site`. It writes nothing under `status/`. Proved by AC-1 to AC-6.
3. **Content.**
   - The index, newest first: tag (linking to its page), publication date, prerelease or not, the overall gate mark, the advisory status mark and the package count.
   - A release page: tag, date, the ISO's SHA-256; the gates at release (SBOM, licences, CVEs, unowned, overall) from `attestation-summary.json`; the CVE scanner and its version, the DB build date, the coverage counts and the gating findings; the unowned count and files; the current advisory status from `status/<tag>.json` (`status`, `checked`, `advisories`, `clearing`, `grype_db_built`); the SBOM's packages with version and licence, and a licence summary (packages per licence); a link to every release asset; and the verify command. For this repository's releases that is the command `release-notes.sh` prints (`gh attestation verify themonolith-<version>.iso --repo <repo> --signer-workflow <repo>/.github/workflows/build.yml`); for rc1 it is P01-AC-2 (b)'s, naming `tuckermclean/linux-live-iso-factory`.
   Proved by AC-1 and AC-2.
4. **Workflow.** `advisory-feed.yml` keeps its cron and `workflow_dispatch` and adds `workflow_run` on the `Release` workflow's completion; a Release run that did not succeed starts no scan. `make dashboard` runs between `make advisory-feed` and the Pages upload and does not stop the feed's publication when it fails: the status files are published without the pages, and a last step (`make dashboard-check`) ends the run red. No new action, no new permission. Proved by AC-5 and AC-6.
5. **Ledger.** `docs/capabilities.md` lists the release dashboard under "Release and after" as P04, mode `build`, and keeps the in-browser boot demo and the predecessor's dashboard code under "Dropped". `docs/migration.tsv` is unchanged. Proved by AC-7.

## Risks
- Adding an asset changes every release's `SHA256SUMS` from the next tag on; the attestation's subject stays the ISO. Releases published before this node have no `attestation-summary.json` and show their gates as `not published`.
- `deploy-pages` replaces the site: a run that publishes nothing (P03's failure paths) also leaves the previous pages in place, and a dashboard failure publishes the feed without pages until the next run.
- `workflow_run` chains are limited to three levels (Build → Release → Advisory feed is three), and a Release run started by `GITHUB_TOKEN` triggers `workflow_run` only because it is a workflow completion, not an event the token created (unverified until AC-8's release run).
- Stele's CSS support (`prefers-color-scheme`, grid or flex layout) is unverified; the pages must read in its fallback (light theme, block layout).
- The size of a release page grows with the SBOM (166 packages for rc1); no pagination is planned.
- OD-1: the pages share the advisory name; if it lapses, the dashboard goes with the feed.
