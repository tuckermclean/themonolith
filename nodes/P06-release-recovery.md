## Purpose
The `v0.2.0-alpha1` tag published nothing. Its Build run (44657368653) failed a boot check in attempt 1, so `release.yml` skipped itself. A green Build would still have failed at `gh release create`, because the release had been created and published by hand in the GitHub UI, and that is also what created the tag. `docs/releasing.md` offers only delete-the-tag-and-re-tag as a retry, and nobody was told: the operator found out from the empty release. After this node a tag's Build run that is re-run and turns green publishes, and the docs make that the first retry after a flake. A release that already exists for the tag with no assets is filled in, and one with assets stops the publish before anything is pushed. The docs say that pushing the tag is the only operator step. A tag that does not publish opens, or comments on, an issue for that tag.

## Standard mechanism
GitHub Actions' `workflow_run` trigger, which fires again when a re-run attempt of the Build run completes: Release run 44797192287 was started by attempt 2 of Build run 44657368653. Also `actions/upload-artifact`'s `overwrite` input, `gh release view`, `gh release upload` and `gh release edit` for an existing release, and `gh issue list`, `gh issue create` and `gh issue comment` with `GITHUB_TOKEN` for the report. No gap is recorded. The only new code is the branch in `release-create.sh`, a short check script and a short report script.

## Changes from the port
`release.yml`, `build.yml`'s attestation job, `release-create.sh` and `docs/releasing.md` stay as P01 left them except for these changes. The publish condition (`conclusion == success`, P01-AC-4, P01-AC-12) and the digest chain (P01-AC-3) do not change.

1. **A re-run attempt publishes.** `release.yml` keeps reading every artifact by `github.event.workflow_run.id`, which is the same for every attempt of a run, and nothing in it tests `run_attempt`. Every `upload-artifact` step of `build.yml`'s attestation job sets `overwrite: true`. Without it, a re-run of an attestation job that had uploaded some files and then failed would collide with its own earlier upload. `docs/releasing.md`'s retry step (step 6) puts **Re-run failed jobs** on the tag's Build run first, for a failure in which nothing needs fixing (a flake, a runner fault). The run's other jobs keep their results and their artifacts, and when the re-run turns the run green, `release.yml` publishes from it. The fix-forward path (fix on `main`, delete the tag, re-tag) stays for a failure that needs a change. A failed Release run is retried by re-running that Release run. Reason: re-running the failed jobs is the obvious retry and costs no rebuild, but nothing said it publishes (#115). *AC-1.*
2. **An existing release does not break publishing.** A new `publish` step, `Check for an existing release`, runs `make release-existing` after the digest chain and before `Push the distfiles archive`. The target runs `scripts/release-existing.sh`, which asks `gh release view` for a release for the tag, draft or published. With none, or with one that has no assets, it exits 0. With one that has assets, it exits 1, so the job stops before the distfiles push and uploads nothing. Its message names the tag and the asset count, and says to delete the release while keeping the tag (`gh release delete <tag> --yes`, without `--cleanup-tag`) and then re-run the Release run. The check is a script of its own, and neither the script nor its Make target contains the string `gh release create`: P01's `release-workflow.test.sh` takes the first `publish` step whose text, with the scripts and `make -n` output it names, contains that string as the release step (P01-AC-4's order, P01-AC-9's prerelease flags), so a step before the push that named `release-create.sh` would be read as the release step. `release-create.sh` stays in the `Create the GitHub release` step and holds the create and fill paths. With no release for the tag it calls `gh release create` as today. With one that has no assets, it uploads the assets with `gh release upload` and then sets the title, the notes, the prerelease and Latest flags (the same rule as P01-AC-9) and `--draft=false` with `gh release edit`. It never calls `gh release create` in that case. With one that has assets (uploaded after the check ran), it exits 1 with the same message and uploads nothing. Reason: a release made by hand stopped `v0.2.0-alpha1`, and an empty one can be filled without losing anything (#115). *AC-2.*
3. **A tag that did not publish is reported.** `release.yml` gains a `report` job that `needs` `resolve` and `publish` and runs `if: always()` for a `push` Build run. It calls `make release-report`, and `scripts/release-report.sh` reports when the Build run's conclusion is not `success`, or when the Release run's `resolve` or `publish` job failed, and in either case only if `head_branch` is a tag that points at `head_sha`. A branch push reports nothing. The report goes to the open issue titled `Release <tag> did not publish`: the script creates the issue if none is open and adds a comment otherwise. The text names the tag, the Build run's URL, its attempt and conclusion, the jobs that failed or were cancelled (from `gh run view --json jobs` for that attempt), the Release run's URL when the failure is the Release run's own, and a link to `docs/releasing.md`'s retry step. The `report` job alone gets `issues: write` and `actions: read`, and `release.yml`'s top-level permissions do not change. Reason: the failure showed only in the Actions tab (#115). *AC-3.*
4. **The release is never made by hand.** `docs/releasing.md`'s operator steps say that pushing the tag is the only step. They say not to create, draft or publish the release for the tag in the GitHub UI or with `gh release create`, because publishing a release there also creates the tag and starts the Build. They also say what the pipeline does with a release that already exists (change 2). *AC-4.*

## Risks
- Unverified: whether `actions/upload-artifact`'s `overwrite: true` replaces an artifact that an earlier attempt of the same run uploaded, and whether `download-artifact` with `run-id` then returns the replacement. The first slice checks it, from the documentation or a recorded re-run.
- `gh release view` on a draft needs a token that can see drafts. `contents: write` covers it (unverified for drafts made in the UI).
- A report issue opened by `github-actions[bot]` notifies the repository's watchers. It is not labelled for the loop, so the loop does not triage it.
- Changes to `.github/workflows/*` need a token with the `workflow` scope to push (AGENTS.md traps). `issues: write` is a new permission in the release path, and the owner reviews it (SPEC §8: fewest permissions, on the one job that needs it).
- `release.yml` runs from the default branch (`workflow_run`). The `report` job therefore takes effect only once it is merged, and a throwaway tag tests the merged copy (AC-3's record after the merge). A fault that run finds is fixed by a follow-up PR.
- P04's `dashboard-workflow.test.sh` stubs `gh` with a script that answers every call with exit 0 and no output, so `release-create.sh`'s `gh release view` sees exit 0 and no JSON there. The script must still upload every asset in that case (P04-AC-7, AC-5).
