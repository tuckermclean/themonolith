## Purpose
The recipes and the distribution policy that build the world set come in here, together with the build that proves them: B01's slow criteria build `world`. The package build runs from this repository against GHCR and the pinned tree, with the predecessor's behaviour. Afterwards a package counts as built only if it is installed at its locked version, and every world atom is locked. The development cache is keyed on the inputs Portage cannot see. A release build compiles every package that reaches the rootfs in that run, and proves it, except a short declared list of toolchain files. Every file in the final root filesystem is accounted for: installed unchanged by a package, generated by a named step, or declared. A rebuilt static library rebuilds its cached consumers, shown by a real build.

## Standard mechanism
Portage `PKGDIR` with gpkg, `--usepkg`, `--binpkg-respect-use=y`, `--binpkg-changed-deps=y`, `--rebuild-if-unbuilt`, `portageq has_version`, `package.mask`. Custom code that remains, all ported:
- `binpkg-store.sh` (OCI transport of one `PKGDIR`): a binhost over HTTP needs a web host we lack (SPEC §5).
- `savedconfig-cache.sh`: Portage does not hash savedconfig contents (script header, `savedconfig-cache.sh:3-12`).
- `versions.lock` and `update-versions.sh`: SPEC §5 "Versions".
- New: the cache tag hashes `make.conf`, `bashrc`, `env/`, `package.env` and `profile/` because Portage cannot see them. This is a few lines of `sha256sum` in the existing script. A per-package fingerprint was considered; the cache tag is enough.

## Changes from the port
1. **Cache tag.** `binpkg-store.sh` tags the artifact `binpkgs:<tag>` (SPEC §6), with `<tag>` the first 16 hex of sha256 over `BUILDER_DIGEST`, `TREE_COMMIT` and a hash of `make.conf`, `bashrc`, `env/`, `package.env/`, `profile/`. The predecessor keyed on `BUILD_EPOCH` alone (`binpkg-store.sh:59`, `build.yml:269`), so a `bashrc` edit reused stale binaries. Only `main` pushes; PRs pull; tags do neither (the predecessor pushed with `if: always()` and no ref condition, `build.yml:448-450`). The first `main` build is cold (~75 min measured). rc1's cache is not seeded. *AC-1, AC-2.*
2. **Emerge flags.** The predecessor passes only `--jobs --load-average --keep-going --buildpkg --usepkg --verbose` (`build-packages.sh:242-249`), and `make.conf` has no `EMERGE_DEFAULT_OPTS`. Add `--binpkg-respect-use=y --binpkg-changed-deps=y --rebuild-if-unbuilt` when `--usepkg` is on. Portage defaults for the first two are unverified, so passing them is free. *AC-3.*
3. **Success is the installed set, not a glob.** On the failure branch `compgen -G ".../${PKG_NAME}-*.gpkg.tar"` (`build-packages.sh:295`) counts any gpkg of the package, of any version, including one restored from the cache. A failed rebuild with `--keep-going` therefore counts as built. Replace it with `portageq has_version` on the target root for the locked `=cat/pkg-ver` atom. The success branch (`:253-259`) is kept, since a zero exit under `--keep-going` means nothing failed. *AC-4.*
4. **Locked or fail.** A world atom with no lock line currently queues as `(latest)` (`build-packages.sh:192-198`) and `update-versions.sh update` drops unresolvable atoms with a warning (`update-versions.sh:152-160`). Both now exit non-zero. Regenerate `versions.lock` with the ported `update-versions.sh` to close the 23-atom drift; it locks `monolith-base` at R01's `-r7` (99 world atoms, 77 lock lines at b9f533b). Atoms with operators or slots (`<sys-fs/ncdu-2`, `=games-roguelike/nethack-3.6.7-r1`, `net-misc/iperf:3`) are among the 23. *AC-5, AC-6.*
5. **Tag builds prove source.** The ported `MONOLITH_USEPKG=n` (`build-packages.sh:221-225`) stays. Add: with it set, `PKGDIR` must be empty at start, and the emerge log must contain no `>>> Emerging binary` line (the format the script already greps, `build-packages.sh:413`). *AC-7.*
6. **Removed things stay removed.** `package.mask` covers man-db, fortune-mod, usbutils and nmap. The doctrine list also names w3m, thttpd and on-target gcc, which are masked nowhere. Add `www-client/w3m`, `net-www/thttpd`, `sys-devel/gcc` (target root only, to be confirmed so the host toolchain is untouched) to `package.mask`. A fast test checks the doctrine.yaml list against `package.mask` and `world`. *AC-8.*
7. `savedconfig-cache.sh` TRACKED list gains the kernel (B02 owns that line).
8. **Release mode reuses nothing.** With `MONOLITH_USEPKG=n` the predecessor emerges only the world atoms (`build-packages.sh:221-250`). Dependencies already installed in the builder image's target root are therefore skipped, not rebuilt. `quickpkg --include-config=y "*/*"` then repackages every installed sysroot package without compiling it (`build-packages.sh:319-324`, with `2>/dev/null || true` at `:323`). The whole sysroot is rsynced into the rootfs (`build-packages.sh:342-376`). So a release could ship binaries that were never built in that run. In release mode:
   - `PKGDIR` starts empty and `--usepkg` is off (change 5);
   - the `quickpkg` step does not run;
   - before the emerge, `build-packages.sh` lists the target VDB that the builder image ships (`/usr/${CROSS_TARGET}/var/db/pkg`) and adds each package found there to the emerge command line as `cat/pn:slot` with `--oneshot`. Portage always re-merges a package named on the command line, so each one is compiled again in this run; `--oneshot` keeps it out of the world file. The list is printed in the build log.

   A release build starts in a fresh container from the builder image, so everything else in the graph is compiled anyway. The preinstalled packages are the only ones that could be reused. `--emptytree` was considered and rejected: it re-merges the same set, plus anything crossdev placed in the target root, and in a cross build it may also pull build-host dependencies into the graph (unverified). Naming the preinstalled packages rebuilds exactly the set that would otherwise be reused, and the source audit (change 9) proves the result.

   Development mode keeps the ported behaviour. *AC-10.*
9. **Source audit of what ships.** After the sysroot export (`build-packages.sh:342-376`), `scripts/source-audit.sh` assigns every file in `output/sysroot/` to its owner in the target VDB (`/usr/${CROSS_TARGET}/var/db/pkg/*/CONTENTS`). It then fails in any of three cases:
   - a file's owning cpv was not merged from source in this run, judged from emerge's own `>>> Emerging (N of M) <cpv>` lines in this run's log, cross-checked with `BUILD_TIME` at or after the run's start;
   - a file has no owner and is not in `configs/attestation/bootstrap-exceptions.txt`;
   - an exception entry matches no file.

   The report, `source-audit.tsv` (`path`, `owner`, `built-this-run`|`bootstrap`), is a release asset. *AC-11, AC-12.*
10. **Declared bootstrap exceptions.** The crossdev toolchain installs some files into the sysroot from host-side `cross-i486-linux-musl/*` packages. They are owned in the host VDB, not the target VDB. The known case is the musl `libc.so` copied to `/lib/ld-musl-i386.so.1` (`build-packages.sh:380-389`; R03 removes it).
    - `bootstrap-exceptions.txt` lists each such path with its host owner, found with `qfile` on the host root. Every line names a cpv whose version equals `crossdev.lock`.
    - The pinned `BUILDER_DIGEST` is the provenance of these files.
    - Code that the toolchain links into every static binary (musl `libc.a`, `libgcc.a`, `libatomic.a`, `libssp_nonshared.a`) is not a rootfs file. Its provenance is also `BUILDER_DIGEST`, and SPEC §6 says so.
    - Nothing else may be listed. A preinstalled package that cannot be re-merged in the sysroot is a finding to fix, not an exception. *AC-12.*
11. **`rl144` and `stele` are left out of `world` for MS1.** They fetch Rust crates while they build, so they cannot build in the offline release mode (P02). Leaving them out lets the iteration ISO land without waiting for R05, which restores them and is mandatory before the first release (P01-AC-11). Remove their `world` lines (`world:253-256`, `:295-300`) and their `versions.lock` lines. Their ebuilds are not ported here; R05 ports them. Add two lines to `docs/rc1-diff-reasons.tsv` (P01) naming R05 as the reason. B03 runs every boot mode except `stele-acid2` until R05 restores it. *AC-13.*
12. **Provenance of the final root filesystem.** The source audit (change 9) covers `output/sysroot/`, but the squashfs is assembled from more than that:
    - `build-rootfs.sh` creates directories and symlinks (`build-rootfs.sh:41-60`), writes the `/etc` files and init scripts (`:192-671`), indexes the X fonts (`:107-160`), sets `/bin/sh` and `more` (`:685-693`) and bakes the mandoc database (`:714`);
    - package `pkg_postinst` hooks leave files that no `CONTENTS` lists, such as `etc/ld.so.cache`, `etc/profile.env` and the binutils-config links.

    The ported unowned gate already sorts these files. `check-unowned.py` reads the rootfs VDB's `CONTENTS` (`check-unowned.py:58-80`) and suppresses the rest through `unowned-allowlist.yaml`, whose comments say where each entry comes from. It stops at "owned or allowlisted". It does not check that an owned file still has the bytes its package installed, or that an allowlisted file came from the step its comment names. Extend that gate rather than add a second one:
    - **Mode.** `check-unowned.py --provenance --package-tree output/sysroot [--source-audit source-audit.tsv]`. `attestation.sh` runs it on the root filesystem extracted from the built squashfs, so it checks what ships. Without `--provenance` the script behaves as ported, which S01's rc1 lane needs.
    - **Package files.** An owned `obj` must have the MD5 its `CONTENTS` line records, and an owned `sym` the recorded target. With `--source-audit` (release mode), the owning cpv must be `built-this-run` there.
    - **Generated files.** Every allowlist entry gains a required `source`: `build-rootfs.sh`, `postinst:<cat/pn>` or `portage` (the VDB itself and emerge's news state). A regular file or symlink classed `generated` by a `build-rootfs.sh` entry must not exist in `output/sysroot/`, so the script cannot quietly replace a package file. A `postinst:<cat/pn>` entry needs that package installed (in release mode, `built-this-run`), and its paths must exist in `output/sysroot/`, where the hook wrote them.
    - **Modified package files.** An owned file that an assembly step rewrites, so that its bytes differ from `CONTENTS`, is listed under a new `modified:` key of the same file, with its `source`. Any other difference fails.
    - **Toolchain files** stay in `bootstrap-exceptions.txt` (change 10). The check reads that file, so no path is declared twice.
    - **Stale entries fail**, as in change 9: an allowlist or `modified:` entry that matches nothing in the rootfs.
    - **Report.** `rootfs-provenance.tsv` has the columns `path`, `class` (`package`, `generated`, `modified` or `bootstrap`), owner or source, and `built-this-run` in release mode. It is uploaded with every build and is a release asset (P01).

    The allowlist comments already name a source for almost every entry, so the `source` fields are an edit, not research. The first run on a real build shows any that are wrong. MS1 builds run the mode without `--source-audit`; releases run it with. *AC-14, AC-15.*
13. **A rebuilt static library rebuilds its cached consumers.** Every rootfs binary links its libraries statically, so a consumer restored from the cache keeps the old library code inside it. Change 2's `--rebuild-if-unbuilt` is meant to rebuild it, but nothing shows that it does with a cross `ROOT` and a restored `PKGDIR`, and checking the flag on the command line (AC-3) only shows that it was passed. `scripts/tests/static-rebuild.itest.sh` checks the result with real builds:
    - **Fixture.** A two-package overlay in `scripts/tests/fixtures/static-rebuild/`. `monolith-test/libmarker` installs only `libmarker.a` and its header; the library returns the string `LIBMARKER-${PVR}`, or `LIBMARKER-${PVR}-alt` with `USE=alt`. `monolith-test/usemarker` has libmarker in `DEPEND` only, as a static consumer does, and links a static binary that prints that string.
    - **Runs.** Each step is a fresh container from the pinned `BUILDER_DIGEST` with the pinned tree, as each CI run is, so the target root starts empty. Only a scratch `PKGDIR` carries over between steps, as the GHCR cache does between runs. Each step runs the ported `build-packages.sh` in development mode, with `CONFIGS_DIR` pointing at a copy of `configs/` whose `world` is `monolith-test/usemarker`, whose `versions.lock` locks both packages and whose `repos.conf` adds the fixture overlay.
      1. Cold: both packages are built from source.
      2. Control, nothing changed: both come from the cache (`>>> Emerging binary` for each). This shows the cache is used, so the next steps test something.
      3. libmarker revbumped to `-r1`: both are built from source, not from the cache, and the installed `usemarker` binary contains `LIBMARKER-1-r1` and not `LIBMARKER-1`.
      4. `package.use` gains `monolith-test/libmarker alt`: both are built from source, and the installed binary contains the `-alt` string.

      Strings are read with `grep -a`; nothing i486 runs on the host.
    - **Where it runs.** `make test-static-rebuild` locally (Docker and the builder image needed), and a `build.yml` job next to the package build (B03 wires it). A failure fails the run.
    - **If it fails.** The fix is a Portage option, not a script, for example `--rebuild-if-new-rev` or `--changed-deps=y`, and the test picks it. Until one passes, development builds run with `MONOLITH_USEPKG=n` (cold, about 78 min measured) rather than ship stale consumers. A failure does not block MS1; it makes MS1 builds slower.

    *AC-16.*
14. **GHCR storage, auth errors fatal.** `binpkg-store.sh` builds its reference as `${REGISTRY}/binpkgs:<tag>` from I01's variable, replacing `ghcr.io/${owner}/monolith-binpkgs` and the `GHCR_OWNER` plumbing (`binpkg-store.sh:68-75`, `build.yml:199`). The Makefile's `S3_BUCKET` and `restore-cache` (`Makefile:66-67,153,376-377`) are not ported. `_bp_pull_is_benign_miss` treats `unauthorized|denied|401` as a cache miss (`binpkg-store.sh:330-338`) because a never-pushed GHCR repository answers 401 (`binpkg-store.test.sh:113-116`). That also hides an expired token or a private package, and the build then silently compiles from source (SPEC principle 5). The regex keeps `not found|manifest unknown|name unknown|404` and drops `unauthorized|denied|401`, and the test's `benign` cases at `:114-116` become `fatal` cases. To keep the first pull from failing, the owner pushes any artifact to the package once (Step 0) before CI relies on it. The "Save binary package cache" step stays warn-only, since the cache only speeds builds up (SPEC §6), but a failed `pull` fails the job. *AC-17, AC-18.*

## Risks
- Whether `--rebuild-if-unbuilt` works with a cross `ROOT` and a restored `PKGDIR` is unverified until AC-16 runs. Releases build from source, so a miss cannot reach one; change 13 says what development builds do if it fails.
- Some allowlist sources will be wrong on the first real run (AC-15), for example where a postinst file turns out to be written by `build-rootfs.sh`. Each is an edit to a `source` field, not a code change.
- The initrd is not checked file by file. Its binaries are copies of sysroot files (`build-initrd.sh:23,120,230`) and its scripts come from `rootfs/` in this repository. A content-hash check against `rootfs-provenance.tsv` is the natural extension if one is wanted.
- The exact `portageq has_version` form against the cross root is unverified; `update-versions.sh:64` shows the `PORTAGE_CONFIGROOT` shape.
- Masking `sys-devel/gcc` may break the host toolchain if the mask is mirrored host-side (`build-packages.sh` mirrors `package.mask`). Check before adding it.
- What the builder image's target VDB holds is unknown. The predecessor's comment names `acct-user/*` (`build-packages.sh:319-320`). If it also holds crossdev-placed packages (for example `sys-kernel/linux-headers` or `sys-libs/musl`), re-merging one with the cross compiler may fail. The owner then decides before release: fix the rebuild, or justify the files as toolchain files in `bootstrap-exceptions.txt` with their host owner. Silent reuse is not an option.
- `monolith-base`'s help topics still name rl144 (`topics/games.txt:11`, `topics/tools.txt:40`) on MS1 iteration ISOs, before R05. They are left as they are: R05 makes them true again, and editing them needs a `monolith-base` revbump.
- The GHCR quirk behind change 14 (a never-pushed package answers 401) is the predecessor's observation, not re-verified. If no first push happens before the first build, AC-17 makes the first pull fail loudly, which is intended.
