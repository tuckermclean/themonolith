## Purpose
In the `v0.2.0-alpha1` tag run (Build run 44657368653, attempt 1), the `bios (64)` boot failed one check: `guestbook.cgi inserts + reads back a row via sqlite3` exited 255 while perl compiled `CGI.pm` → `CGI/File/Temp.pm` → `parent.pm` → `File/Temp.pm` line 149. The first line of perl's message, the error itself, was cut off, because a failing check reports only the last 500 characters of its output. The `CGI.pm param()` check just before it passed. The same job passed in attempt 2 of that run, on the same ISO, and the `main` push of the same commit (run 44207204793) passed it too. The leading suspect is memory, since the guest has 64 MB and this check loads the heaviest perl chain of the boot, but nothing recorded the guest's memory. The failure also looks like #46's `uefi` failures (perl dying while it compiles a module, then passing on a re-run), which O03 closed as not reproduced. After this node a failing check shows the start of its output and the guest's memory, the cause is found from a recorded failing run and fixed where it lies (or recorded as not reproduced), and `bios (64)` passes 20 times in a row in CI. A check that fails only some of the time on the same ISO does not stay a release gate without that record.

## Standard mechanism
The harness as O01 and O03 left it (`boot-test.py`, `boot-test.yml`, `boot-test-repeat.yml`), the guest's `/proc/meminfo` and busybox `dmesg`, and GitHub Actions' job matrix for repeated boots. No gap is recorded. The only new code is the output clipping of change 1 and one more evidence command.

## Changes from the port
`boot-test.py`, `boot-test.yml`, `boot-test-repeat.yml` and the `test-boot` target stay as O01 and O03 left them except for these changes.

1. **A failing check shows the start of its output.** Every validator in `boot-test.py` that puts a check's output into its failure detail (today `output.strip()[-500:]`, or `[-200:]` in `epoch_close_to`) uses one helper instead. Output of up to 1,000 characters is reported whole. Longer output is reported as its first 500 characters, a line `[… <n> characters cut …]`, and its last 500 characters. No validator's pass or fail decision changes. Reason: perl prints the error first and the `Compilation failed in require` chain after it, so the tail alone hides the cause (#115). *AC-1.*
2. **A failing check records the guest's memory.** `failure_evidence` (O03 change 1) runs `cat /proc/meminfo` first, before the `sha256sum`, the `dmesg` tail and the second run, and prints it under its own label. Reason: whether the guest was short of memory at 64 MB is #115's first question, and nothing recorded it. *AC-2.*
3. **The perl CGI checks checksum the modules of the failing chain.** `PERL_CGI_FILES` gains the installed paths of `CGI/File/Temp.pm`, `parent.pm` and `File/Temp.pm`, as `%INC` names them on the disc (expected under `/usr/lib/perl5/5.42.0/`). Reason: these are the files perl was reading when it failed, and their hashes, compared with the run's squashfs, say whether the guest read the bytes on the disc. *AC-3.*
4. **Repeated `bios` boots at 64 MB without a rebuild.** `boot-test-repeat.yml` gains a `mode` input with the choices `uefi` (the default, so O03's runs are unchanged) and `bios-64`. With `bios-64`, each matrix job runs `make test-boot MODE=bios RAM_MB=64` on the downloaded ISO and uploads its serial log and `tool-versions.txt` under a name that carries the mode and its matrix index. It passes `toolbox/ci lint`. Reason: AC-6 needs many `bios (64)` boots, and a full build per boot costs a build each time. *AC-3, AC-6.*
5. **The fix lies where the cause is.** When AC-5's record names a cause in this repository, the fix is made in the file that holds it: B01's perl recipe or overlay, the rootfs build, or O01's `boot-test.py`. The record names the file and the line. Two kinds of cause go to the owner as a spec change before anything is changed. The first is a cause outside the repository (QEMU, SeaBIOS or the toolbox pins, the runner image). The second is a remedy that changes what 64 MB supports: a smaller CGI path, a swap file, moving the perl CGI checks out of the 64 MB boot, or a documented floor below which they are not claimed. The 64 MB floor is SPEC §1's claim and §10's tracked concern, and the owner settles it. *AC-5, AC-6.*

## Gate
- **O04-AC-1** — A failing check whose output is longer than 1,000 characters reports its first 500 characters, a `[… <n> characters cut …]` line with the right count, and its last 500 characters. Output of 1,000 characters or less is reported whole. Each validator's pass or fail result is unchanged for the same exit code and output. *Verify:* `scripts/tests/boot-test-bios64.test.sh`: a fake child whose guestbook command exits 255 with a 3,000-character perl error whose first line is unique, and the detail contains that line; `contains`, `regex_matches`, `regex_absent`, `exit_code_only`, `contains_with_exit` and `epoch_close_to` each on an output of 999, 1,000 and 1,001 characters.
- **O04-AC-2** — When a check that names files fails, its detail contains the guest's `/proc/meminfo` (a `MemTotal:` and a `MemAvailable:` or `MemFree:` line) before the `sha256sum` lines. A check that passes runs nothing extra (O03-AC-1). *Verify:* `scripts/tests/boot-test-bios64.test.sh` (fake child).
- **O04-AC-3** — `PERL_CGI_FILES` names O03's six files and the three modules of change 3, and the `CGI.pm param()` and `guestbook.cgi` checks still pass it as their `files`. `boot-test-repeat.yml` accepts `mode: bios-64`, runs `make test-boot` with `MODE=bios` and `RAM_MB=64` for it and with `MODE=uefi` by default, and passes `toolbox/ci lint`. *Verify:* `scripts/tests/boot-test-bios64.test.sh` (the tuple; a grep of the workflow); `toolbox/ci lint`; a `uefi` artifact of an O03-style run and a `bios-64` artifact of an AC-6 run.
- **O04-AC-4** — Nothing hides the failure. `should_retry_launch` still never relaunches after a failure that came once `/init` was reached (O01-AC-1). The `bios` mode still runs the `CGI.pm param()` and `guestbook.cgi` checks with their `contains` validators and commands unchanged, `build_bios_cmd` still runs `-cpu 486` with `-m` from `--ram-mb`, and `boot-test.yml`'s `ram_mb` matrix is still `[64, 256]`. O03-AC-3 still holds for `uefi`. A change to any of these needs a spec change first. *Verify:* `scripts/tests/boot-test-retry.test.sh` and `scripts/tests/boot-test-evidence.test.sh` (unchanged); `scripts/tests/boot-test-bios64.test.sh`.
- **O04-AC-5** — `docs/evidence/bios64-flake.md` lists every CI `bios (64)` boot of a built ISO from Build run 44657368653 attempt 1 to the end of AC-6. Each row has its job URL, the ISO's sha256, the runner CPU model and the result. The record starts from the evidence that attempt 1's job log already holds (O03 change 1: hashes, `dmesg` tail, a second run). It says whether the failure has #46's signature, and it states one of three outcomes. (a) A failing boot with this node's evidence: what the head of perl's output, `/proc/meminfo`, the hashes (compared with `unsquashfs` of that run's squashfs), the second run, the `dmesg` tail and the runner CPU show; the cause; and the fix with its file and line (change 5). (b) The cause needs a remedy that change 5 sends to the owner: the record names the cause and the owner's decision, and the fix follows that decision's spec change. (c) No `bios (64)` boot fails once changes 1 and 2 are in place, up to the end of AC-6's 20 consecutive passes: that record is the outcome, and the failure is recorded as not reproduced. *Verify:* the file, linked in the PR table, with every run URL it cites.
- **O04-AC-6** — With changes 1 to 4 in place, and the fix of AC-5 (a) or (b) if there is one, 20 consecutive CI `bios (64)` boots pass on GitHub-hosted runners. They boot ISOs built by `build.yml`, at least two different ISOs among them, through `boot-test.yml` or `boot-test-repeat.yml` with `mode: bios-64`. A failing boot restarts the count and goes into AC-5's record. No failed job is re-run to turn it into a pass. *Verify:* the run URLs in `docs/evidence/bios64-flake.md`, recorded in the PR table.

## Risks
- The rate is unknown: one failure among the `bios (64)` boots since O03, and attempt 1's job log is the only failing record. At a low true rate, AC-6 can pass with the fault still present. AC-5 (c) records it as not reproduced, and the issue can be reopened from a later failure's evidence, which changes 1 and 2 make readable.
- If the cause is memory at 64 MB, the fix is a judgment about what 64 MB supports (SPEC §1, §10's 8 MB row). Change 5 sends it to the owner, and the node waits for that spec change. A swap file needs a writable disk that the live boot does not have.
- `/proc/meminfo` read after the failure shows memory once perl has exited, not at its peak. An OOM kill or allocation failure shows in the `dmesg` tail and in perl's first line (change 1), which is why both are kept.
- `boot-test-repeat.yml` downloads another run's ISO with `run-id` and needs that artifact's retention (O03 Risks).
