## Purpose
After this node a Gentoo tree is pinned by the SHA of a commit in `github.com/gentoo-mirror/gentoo`, ingested once as a deterministic archive into the store `snapshot` class, and every build extracts it from the store with no network. The mirror's git history is what survives of the tree rc1 was built from: the dated snapshot tarball (`gentoo-20260811.tar.xz`) is gone from the dead S3 account and from upstream. The first pin is the commit whose ebuilds match rc1's binary packages byte for byte, so rc1's cache stays valid (OD-6 default). Later epochs may pin a newer commit or an official signed daily snapshot. A missing or corrupt pin fails loudly.

## Scope
In:
- `probe`: report what signature, if any, a commit or its top-level `Manifest` carries (the first slice).
- `match-rc1`: choose rc1's commit by comparing the ebuilds embedded in rc1's gpkgs; record the commit and the report.
- `commit-at`: the last commit at or before a time (also gives M02 the 20260810 toolchain tree).
- `seed`: fetch a commit's tree, archive it deterministically, `store put` the archive and a metadata sidecar.
- `stage`: store to a directory that the build mounts as `/var/db/repos/gentoo`; no network.
- Later, off the critical path: `seed-daily`, `latest`, `cross-check` for official signed daily snapshots.

Out:
- Which commit is current and bumping it: I05 (ledger), M01 (`BUILD_EPOCH` bumps), M02 (`TOOLCHAIN_EPOCH` bumps).
- The builder image and its stage3: I03 (adopts rc1's), M02 (rebuilds it from the 20260810 tree).
- Mounting or copying the tree into the build, and `package.mask` mirroring to the host: B01.
- Retention of snapshots: M03 (forever).
- Store backends: F06, I01. The rc1 binpkg seed that `match-rc1` reads: I01 (`store-adopted`), used also by I06.

## Design
**The decision (OD-6).** Default: rc1's tree. The alternative (a current tree) is cheaper for I02 but invalidates rc1's whole cache and makes the SBOM diff against rc1 large. The mechanism below serves either: only the commit in `pins.yaml` differs.

**Store keys (SPEC §5, class `snapshot`).** `gentoo-<commit40>.tar.xz` and `gentoo-<commit40>.json`. `<commit40>` is a full lowercase 40-hex SHA. The sidecar holds `{commit, tree_id, commit_time, parent, source, file_count, tar_sha256, files_sha256, signature: {class, detail}}`. `tar_sha256` is over the uncompressed tar; `files_sha256` is over the sorted `path<TAB>sha256` list of regular files (the check `stage` can recompute without git). Daily snapshots keep the predecessor shape `gentoo-<YYYYMMDD>.tar.xz[.gpgsig]`. Rejected: a tag or branch name as the pin; only a full SHA names immutable content.

**Fetch.** `snapshot seed <commit>` makes a fresh `git init`, then `git fetch --depth 1 https://github.com/gentoo-mirror/gentoo.git <commit>`. GitHub allowing a fetch by SHA is unverified; the fallback is `--shallow-since` the commit's date followed by checking the commit is present. `SNAPSHOT_GIT_URL` overrides the URL (tests use a local fixture repository). The repository carries `metadata/md5-cache` (stated by the owner, to be confirmed by AC-21), so the extracted tree needs no `egencache` run.

**Deterministic archive.** `git archive --format=tar <commit>` (entries get the commit time, uid and gid 0, normalised modes), then `xz -T1`. The tar's pax header names the commit, so equal commits give equal tars. `.gitattributes` `export-ignore` would silently drop files, so `seed` compares the archive's file count with `git ls-tree -r` and refuses on a difference. Rejected: archiving the working tree after checkout (mtimes and umask leak in). Compression bytes depend on the xz version; the pin records both the compressed `sha256` (used by `stage`) and `tar_sha256`, and a re-seed never re-puts an existing key.

**Signature (unverified, so the first slice measures it).** Whether gentoo-mirror commits are signed, by whom, and whether Gentoo publishes a key we can fetch is not known to this spec. `snapshot probe <commit>` classifies, in order:
1. `signed-commit`: `git verify-commit` against the keyring built from `pins/keys/gentoo-repo.asc` gives `VALIDSIG` for the pinned fingerprint.
2. `signed-manifest`: the tree contains a top-level `Manifest` that is a clearsigned file, and `gpg --status-fd` on it gives `VALIDSIG` for the pinned fingerprint. This checks authenticity of the top-level manifest only, not the whole Manifest chain (full chain verification needs `gemato`, a third-party Python package, rejected for now).
3. `unsigned-hash-pinned` (the stated fallback): neither is available. The commit SHA is a content hash, so the tree cannot change under the pin; its authenticity rests on (a) the owner reviewing the pin PR and (b) cross-checks: for rc1's commit, the byte-for-byte match against rc1's gpkgs (`match-rc1`); for later commits, `cross-check` against the official signed daily snapshot of the same day (ebuild, eclass and profile file hashes; differences are listed, not hidden).
The probe's result is written to `docs/evidence/i02-signature-probe.json` and to the pin as `tree.signature`. `check-pins` (I05) requires the field, so `unsigned-hash-pinned` is always visible in review. The pinned fingerprint is taken from Gentoo's published key lists when the first slice finds the key; the predecessor recorded `DCD05B71EAB94199527F44ACDB6B8C1F96D8BF6D` for the *daily snapshot* key (`Dockerfile:68-69`), which may differ from the repository signing key. `seed` refuses a signature class weaker than the pin's declared `tree.signature` mode.

**Recovering rc1's tree (`match-rc1`).** `snapshot match-rc1 --seed <dir> --since 2026-08-10T00:00:00Z --until 2026-08-11T06:00:00Z` reads the unpacked rc1 binpkg seed (`store-adopted get binpkg-seed`, I01). For each gpkg whose cpv is not an overlay package, it extracts the embedded ebuild from the gpkg metadata archive (that gpkg metadata carries the ebuild is assumed, as in I06; AC-19's fixture is built from a real rc1 gpkg to settle it) and computes its git blob id. It then asks `git cat-file --batch-check` for `<commit>:<cat>/<pn>/<pf>.ebuild` at every candidate commit in the window and counts equal blobs. It prints the commit with the most matches, and writes every package, the commits it matches at, and any mismatch to `docs/evidence/i02-rc1-tree.tsv`. The pin is accepted when all non-overlay ebuilds match. Otherwise the best commit is used and the mismatching packages are listed; I06's seed drops them and they rebuild. Spot check by the owner: 25 of 25 sampled `versions.lock` entries exist at `d4d0b0c78bd9a3b0b81434268dd96e6f97b294cb` (2026-08-10T22:30Z). Eclass changes are not seen by an ebuild comparison; they are covered because the commit is part of I06's global key and the release rebuilds from source.

**Subcommands** (POSIX sh plus `git`, `gpg`, `tar`, `xz`; diagnostics to stderr; only the query commands print to stdout):
- `snapshot probe <commit>`, `snapshot match-rc1 …`, `snapshot commit-at <iso-time>` (prints one SHA; used by M01 and M02).
- `snapshot seed <commit>`: if `store has` the key, confirm the sidecar's `tree_id` equals the fetched commit's tree and exit 0 without putting. Otherwise fetch, probe, archive, check counts, `store put` both objects, print `tar sha256` and `sha256`. Same key with a different body exits 4 (store immutability).
- `snapshot stage <commit> <dir> [--sha256 <hex>]`: `store get` both objects, check the compressed sha256 against `--sha256` (the ledger value), extract to `<dir>/gentoo`, recompute `files_sha256` and compare with the sidecar. A missing object exits 3 naming the commit and key. It never calls git, curl or wget. The tree reaches the container as a read-only bind mount (or a copy where the build needs to write `metadata/`), and `repos.conf` has no `sync-type`.
- `snapshot stage <commit> --check`: presence query (equivalent to `store has`); the one yes or no for M01.
- `snapshot seed-daily <YYYYMMDD|latest>`, `snapshot latest`, `snapshot cross-check <commit> <YYYYMMDD>`: official signed daily snapshots and the cross-check; later.

**Why no loopback webrsync any more.** The predecessor served the tarball on `127.0.0.1` because `emerge-webrsync` cannot read `file://` and silently falls back to `distfiles.gentoo.org`, whose re-rolled daily file made the tree drift and voided the cache (`sync-portage.sh:8-17`). That problem exists only because webrsync wants a dated tarball and a mirror. A commit archive is extracted by `tar`; portage then reads a directory. Nothing in the build can reach upstream for the tree, so the invariant "no upstream in the tree path" is kept by construction and tested by AC-5. Decision: no webrsync, no HTTP server, no `GENTOO_MIRRORS` trick. Rejected: keeping webrsync for uniformity with the daily path; it costs a server, a port and a timeout for no gain. A later daily snapshot is also just extracted (`tar --strip-components=1`).

**Toolchain tree.** M02's rebuild of the builder image needs the tree of 2026-08-10. That is another commit of the same repository, found with `commit-at 2026-08-10T00:00:00Z` and seeded the same way. Rejected (unchanged): pinning the `gentoo/portage:<date>` Docker image; Docker Hub already dropped `gentoo/portage:20260811` and it carries no Gentoo signature.

**Failure behaviour.** There is no fallback chain. If the pinned commit is absent from the store, `stage` exits 3 with "tree <commit> not in store: run seed-inputs". If `--sha256` is supplied and differs, exit 5. If the commit argument is empty or not 40 hex, exit 2.

## Traps and doctrines preserved
- **T-portage-snapshot-fetch** (a fallback to a drifting upstream; pruning outage; the predecessor's pinned tarball vanished): the build reads the tree only from the store and cannot reach upstream: AC-5, AC-15, AC-21. A commit SHA cannot drift: AC-13.
- **D-two-epoch-pin-model** (two independent pins; a `BUILD_EPOCH` bump never forces a toolchain rebuild): the tree is parameterised by commit only, with no coupling to the image: AC-5; ledger checks in I05.
- **Principle 2** (inputs mirrored): AC-11, AC-20.
- **T-pin-bump-false-green** (a bump validated against a tree that was not actually available): `seed` is the only way a tree enters; M01 calls `stage --check`. AC-10.
- **Principle 5** (no silent weakening): the signature class is recorded and required in the ledger; the fallback is explicit. AC-17, AC-18.
- **D-state-and-no-hidden-stderr**: AC-9.

## Risks and open questions
- Hardest and unverified: **the signature**. Gentoo may not sign gentoo-mirror commits, or may sign them with a key that is hard to find; the top-level `Manifest` may be absent from the mirror. AC-18 is the first slice for this reason, and the fallback (`unsigned-hash-pinned` plus cross-checks) is stated above so the node does not block on it.
- Recovery may find no single commit that matches all ebuilds, because the original daily tarball was cut by rsync at one instant and the mirror commits at another. The window is wide on purpose; remaining mismatches are dropped from I06's seed and rebuild.
- Unverified: GitHub serves fetch-by-SHA for this repository; the shallow-since fallback is slower. Unverified: archive size (the daily tarball was about 40 to 60 MB, an estimate for the daily file, not for a commit archive).
- Unknown whether portage accepts a `git archive` extraction without a `metadata/timestamp.chk` and without a sync step; AC-21 settles it. The expectation is yes, since `md5-dict` cache entries are validated by content hash, not mtime.
- The snapshot class is forever (SPEC §5). One commit per epoch is tens of MB; thinning is M03's decision.
- If a commit is force-removed from the mirror, the store copy is the only copy; this is why `seed` runs before any pin PR merges.
- OD-6: the default (rc1's tree) assumes the CVE gate can waive 2026-08 CVEs (OD-15). If the owner answers "current tree", `match-rc1` and AC-20 are unnecessary and I06's seed is not used.

## Cost
Three slices: (1) `probe`, `match-rc1`, `commit-at`, the fixtures and the real recovery (AC-16 to AC-20, the part that picks the pin); (2) `seed`, `stage`, `--check`, lint (AC-5, AC-6, AC-9, AC-10, AC-13 to AC-15); (3) the real seed and `tree-accept` job (AC-21). The daily path (AC-1 to AC-4, AC-11) is a fourth, later slice. CI: three short dispatch runs plus one builder pull (1.36 GB) for AC-21. Money: tens of MB of store per commit (estimate).

## Spec defects found
- SPEC §5 lists the `snapshot` key shape as `gentoo-<epoch>.tar.xz[.gpgsig]` only. This node adds `gentoo-<commit40>.tar.xz` and `gentoo-<commit40>.json`; §5 should list both shapes.
- SPEC §6 and I05's ledger format key `snapshots` by epoch with a `gpgsig_sha256`. A commit pin needs `tree: {commit, sha256, tar_sha256, signature}`; I05 must follow (I05 amends its format in this revision).
